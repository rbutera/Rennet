# Rennet

A desktop-native code review tool powered by an LLM coding harness. Rethinks the PR review experience while staying interoperable with the existing system (GitHub PRs and the review lifecycle other people see).

The name is settled: Rennet. Branding history remains in [[Code Review App Branding Questions]].

## Why this exists

- Tools like CodeRabbit can group diffs into cohorts and break a large PR into digestible units of review. But cloud solutions require procurement in an enterprise, which kills adoption at clients like the enterprise client.
- LLM-generated code has inflated PR sizes across the org and review has become the bottleneck. This is the core problem: **make large PRs digestible and reviewable**.
- Nobody trusts fully autonomous review. The human stays the gate; the harness does the structural work (grouping, ordering, narrating, surfacing risk) so the human's attention goes where it matters. Related thinking: [[Perceptual Harness - making the human the gate]].

## Product shape

- **v1 surface:** macOS desktop client.
- **Long game:** cross-platform from the outset (Windows/Linux desktop, mobile companion for review-on-the-go). Every architectural decision gets tested against "does this trap us on macOS or in one shell?"
- **Prior art to study:** [[References/Hunk|Hunk]] (hunk.dev, Modem's review-first terminal diff viewer; confirmed by Rai 2026-08-04 as the reference, corrected from the earlier "native macOS app" assumption). In some ways this is "rebuild Hunk as a desktop app with a mobile companion", but our core use case, digestibility of large PRs, is something Hunk doesn't cover. Note Hunk has NO GitHub PR integration at all (working tree, commit, or piped patch only), so the desktop-GUI + PR-interop slot above it is genuinely empty.
- **Interoperability requirement:** reviews happen here but land as normal PR reviews (comments, approvals, threads) in GitHub. No walled garden, no team-wide adoption required for one person to get value.
- **Trust model:** LLM proposes structure and findings, human disposes. No auto-approve, no auto-comment without a human gate.
- **~~Feature candidate (2026-08-04, possibly the keystone)~~ DESCOPED (Rai, 2026-08-04 evening):** the route-handoff idea (author's pre-PR review travelling with the PR as the reviewer's guided route) is out. Rai's verdict: "a cute idea but will run into too many permissions issues with data protection and privacy and stuff." What SURVIVES: both review modes share one review-state model, and v1 must serve both — reviewing a diff an LLM just generated locally, and reviewing someone else's PR. Only the cross-person route-sharing artifact is gone.
- **Hunk relationship (settled framing):** Hunk is a viewer, this is a review system. A viewer renders a changeset; a review system decomposes it, remembers where you got to, and produces an outcome someone else is waiting on. Hunk degrades at exactly the scale where our thesis begins (issue #247: whole-stream buffering, ~2x memory, 45s on monorepo `git log -p`) and its agent comments are one-way (issue #115, users asking for the reply loop for five months). Never say this publicly in comparative form: Hunk is free, MIT, and endorsed by people we respect. Vocabulary rule: "changeset" stays internal (data model), "PR" goes in copy, generality expressed as "before you open the PR, and after someone else opens theirs".

## Architecture POV (consultant hat)

- Shell choice: Electron acceptable for v1 only if the app is architected so the shell is a commodity. Web-tech UI, all domain logic in a portable core, IPC boundary treated as a public API. Tauri (or native) must remain a realistic port, not a rewrite.
- Performance is a feature: diff rendering at 60fps on huge PRs is the credibility test for a review tool. Virtualized rendering, background git plumbing, no main-thread parsing.
- Rendering: RESOLVED by stack research 2026-08-04. **@pierre/diffs is on npm (1.3.2, Apache-2.0, actively released)**: the Pierre diff renderer as a React 19 library, Shiki-based, with review annotations built in. No portable-core conflict (unlike PierreDiffsSwift). **Spike #1 is DONE and MEASURED: [[Wingman Spike – Pierre Diff Virtualization]]** (2026-08-04). Verdict: use Pierre as-is via **`CodeView`**, never bare `FileDiff`/`PatchDiff` (virtualization is opt-in and silently absent otherwise). At 5,000 changed lines CodeView renders in 81ms, holds 120fps with a 15.4ms worst frame, and mounts 899 DOM nodes; the same diff unvirtualized mounts 97,139 nodes and produces a 493ms frozen frame. Line-level windowing inside a single file confirmed (912 nodes for one 5,000-line-changed file). The `@tanstack/react-virtual` fallback was built and measured, and should be dropped from the plan. Full stack: [[References/Desktop and Mobile Stack 2026]] (one compiled artifact in the whole desktop stack; write-it-not-install-it list totals ~2,000 lines of owned infrastructure: typed IPC, git wrapper, command registry, event store, harness adapters).
- Local-first: the repo is already on disk; the git object store is the database. LLM calls go through the user's own harness/API keys, which is what dodges the procurement problem.
- Substrate verdict from [[References/Lumiere|Lumiere]] recon (2026-08-04): **own repo, confidently.** Lumiere has no CI, is dormant since May, has zero Electron/Tauri precedent, and nothing importable; colocation buys nothing. Copy the toolchain as a template. Lift files, not packages: ark's launchd supervisor and lifecycle-server IPC handshake (ephemeral port + bearer token + discovery file), prawn's REVIEW_RUBRIC and adapter interfaces (GitAdapter/AgentAdapter, already the portable-core shape), prawn's CI regression comparator. Avoid: tmux send-keys harness control, Hatchet, heavy native deps (see daemon-fragility case law). Build fresh: structured diff parsing and line anchoring, which nothing in Lumiere does and which IS the product thesis.
- Proposed repo structure: `core/` (portable domain, zero Node-only imports) + `shell/` (Electron main) + `ui/` (renderer), so the Tauri port stays a port and mobile is another client of core.
- **Implementation architecture: [[Wingman Architecture Plan]]** (2026-08-04) — module boundaries and their enforcement, the event-sourced review-state taxonomy, content-addressed hunk identity across force-pushes, the diff pipeline IRs, typed IPC, the process model, the v1 dogfood MUST/LATER cut, and 30 bead candidates. Notably it **resolves the `@pierre/diffs` virtualization unknown** (spike #1): `Virtualizer`, `CodeView`, and a Shiki worker pool all ship in the package, verified against its type definitions.

## Market reality check (2026-08-04, from discovery agents)

Full detail: [[References/Code Review Tools Market]] and [[Code Review App UX Research]].

- **CodeRabbit shipped cohorting in May 2026** ("Change Stack", using the literal words "cohorts" and "layers"). The mechanic is no longer whitespace; doing it LOCALLY with the reviewer's own harness still is. Vocabulary casualty: "cohort", "layer", and "stack" are all burned as product language.
- **Three native desktop large-PR review apps already exist:** [[References/Scrutiny|Scrutiny]] (macOS, "GitHub's UI wasn't built for 50-file PRs"), [[References/Critiq|Critiq]] ($29 one-time, full BYOK, "AI as Your Spotter, Not Your Replacement", comments sync to GitHub), and [[References/Remiss|Remiss]]. CORRECTION (2026-08-04 LSP prior-art sweep, calibrated): remiss.dev is an AI-completeness AUDITOR (spec-vs-diff claim ledger, silent-deferral detection), NOT the Rust/GPUI diff client — the Rust/GPUI keyboard-first agent-review client is **reviu** (github.com/reviu-dev/reviu). Neither ships any code intelligence. ALSO: Critiq and Scrutiny both headline **LSP-in-the-diff** ("LSP-powered hover, jump-to-def, symbol search in every diff" / "full LSP for 12+ languages, jump to definition, find references"), so LSP navigation is validated-not-novel in this category; the platforms (GitHub post-2021, GitLab, Gerrit, Gitea) have all repeatedly declined to wire code intel into the *diff* surface (blob view only), and the whole agent-era wave (hunk, reviu, Stage, Graphite, tuicr...) ships none. Also: Stage is YC **P26**, not S26. Full sweep with citations in [[Wingman LSP Integration Plan]].
- **The remaining defensible wedge:** local cohorting with your own harness, combined with persistent review state that survives a force-push and a night's sleep (Gerrit patchset model, nobody has combined it with cohorting), plus the reviewer-to-agent feedback loop (Hunk issue #115: users begging, unbuilt), plus mobile (empty), plus emotional positioning around reviewer overwhelm (unoccupied).
- **Research anchor:** defect detection collapses past 200-400 LOC per session and 60-90 min continuous review (SmartBear/Cisco). Sub-400-LOC chunks and free stop/resume are core mechanics.
- **The objection to answer in paragraph one, not the FAQ:** "taking the workflow out of GitHub is a deal breaker" (real enterprise buyer, cubic's Launch HN).
- **Stage (YC Spring 2026) holds the chapters ground, including the local half (HN validation, 2026-08-04).** Pitches verbatim: group changes into "small logical chapters", "ordered in the way that makes most sense to read", per-chapter check items, "once you review all the chapters, you're done". Also ships `stage-cli` (MIT, npm `stagereview`): runs inside your agent, ingests PRs via `gh`, "everything happens on your machine", and implements our residue guarantee. A "Stage is sunsetting" HN post is competitor marketing by a rival's founder (2 points, zero comments), not fact; Stage is live. What Stage does NOT have: multiple concurrent lenses, decision extraction, blast radius, claims-and-evidence, harness choice, state across force-push, mobile. **The lens SET is open ground; the chapters lens alone is not.** "Chapter" joins the burned-vocabulary list.
- **"Lens" is burned as a word (2026-08-04 naming round):** six tools already use it (Mantish "One change, three lenses", diffelens, Caliper "Focused Review Lenses", Storybloq/lenses, diffgazer, adamsreview). Crucially they all mean reviewer PERSONAS (security pass, performance pass: different questions asked of one diff); ours means DECOMPOSITIONS (different shapes the same diff is poured into). The concept survives, the word dies. Replacement candidates: **readings** (textual scholarship) or **projections** (cartography, honest because it admits every view distorts). Decision pending, informed by the lens-validation vocabulary harvest.
- **diffelens already runs Claude Code + Codex CLI + Gemini CLI per lens**, so harness plurality alone is not the moat. The moat is the combination: desktop + persistent review state + PR interop + mobile + decomposition.
- **Naming round 1 (2026-08-04):** longlist of 56, RDAP-checked. Shortlist of 10 in [[Code Review App Branding Questions]]. Top 3: **Alcuin** (scriptorium reforms that made silent reading possible; best story), **Catchword** (the word at a page's foot letting the binder verify order before sewing; only candidate with .dev + GitHub org + npm all free), **Loadline** (the Plimsoll mark: safe to sail, readable by anyone on the dock, before it sails). Ortelius and Alhazen killed by hard collisions. Category copy drafted: "A coding harness points a model at your codebase so it can write. A review harness points models at a change so you can read."

## Feature Inventory (as of 2026-08-04)

Status key: **core** (the thesis), **decided**, **candidate** (proposed, not committed), **open** (needs a decision), **lift** (comes from Lumiere).

### Review engine
- Decomposition of large changesets into digestible sub-400-LOC groups, dependency-ordered into a reading sequence (schema before logic before call sites before UI before tests). **core**
- Multi-lens decomposition: 4 or 5 concurrent lenses over the same changeset (chapters/progression, decision points, others TBD), lenses first-class in the data model. **core, decided 2026-08-04**
- Lens model (UX concepts, 2026-08-04): a lens is a PROJECTION over one shared hunk graph (labels-not-folders). Three species with distinct UI slots: sequence lenses (chapters, the rail), queue lenses (decision points, findings), overlay lenses (risk, gutter heat + index). Fixed-point rule: the hunk under the cursor never moves on lens rotation. Original proposed set (chapters + decisions + blast radius + claims-and-evidence + familiarity) SUPERSEDED by the validation synthesis below. **superseded**
- Coverage semantics (UX concepts): two layers. Universal per-hunk-version read state (reading in any lens covers all lenses) + lens-specific OBLIGATIONS reading cannot discharge (a decision needs deciding, a high-blast hunk needs explicit acknowledgement). Done = all hunks read + all obligations discharged. Skimmed-vs-read distinction for collapsed mechanical groups. Cross-lens disagreement (high-blast hunk in a mechanical chapter) is a computable flare: the structural answer to the mis-grouping tension, and the novel interaction claim with no prior art. Prototype first. **candidate, strong**
- Diff chat design (UX concepts): anchored threads (select range/hunk/chapter) in a right-margin panel with anchor chips; harness switcher is a composer chip populated only by auto-detected harnesses, per-thread memory, per-message switchable; "second opinion" re-asks another harness side by side (Q12 disagreement surfacing organically). Chat private by default; answers promotable to finding (via rubric), draft GitHub comment (behind the gate), or route note; findings demotable to threads. **candidate**
- Post-hoc narrative sequencing: works on any PR, requires zero author behaviour change. **core**
- Structured diff parsing and line anchoring engine. Nothing liftable exists; first engineering spike. **core, build fresh**
- Coverage tracking per group, with a provable residue check so no hunk silently escapes grouping (answer to the mis-filed-risky-hunk tension). **superseded by the noise angle, which IS the residue check made visible (2026-08-04)**
- **Noise angle (the sixth angle, Rai 2026-08-04):** everything that didn't earn a place in the five substantive angles, grouped, categorised, and summarised — "42 files were git moved", "DecisionSnapshot was replaced by Decision so the imports were updated in 23 files". The totality guarantee as a surface: at any point the user can see exactly what they haven't looked at, because every hunk is in SOME angle and noise is the floor. Admission rule (proposed, Fable): a hunk only enters noise when a DETERMINISTIC checker attests the pattern (pure move, import-only symbol swap, lockfile, codegen, format-only, mode-only); the LLM labels and summarises but never admits — one deviating line ejects the hunk into the substantive angles. Coverage: noise groups are attested at group level (a distinct state from line-read), with a spot-check affordance; the publish sheet reports both honestly ("1,847 lines read; 3,912 attested mechanical across 7 verified groups"). **core, ratified**
- Risk-scored groups so attention goes where danger is. **candidate**
- Drag hunks between groups to correct LLM mis-grouping (GitButler interaction). **candidate**

### Workspace and repo model
- **Hard requirement (Rai, 2026-08-04): support both project-based and workspace-based setups as first-class.** Most tools (Codex desktop, Paseo, Orca) assume one-repo-one-project opened at the repo root with tool-managed worktrees; Rai's setup breaks every assumption (sessions anchor at /workspace which is itself a repo, product-repo is a nested repo inside it, product-repo's worktrees live at /workspace/wt/* outside the repo they belong to). **required**
- Data model: four distinct nouns. REPO (identity = git common dir / object store, never a path), WORKTREE (a checkout attached to a repo, anywhere on disk; mapping discovered via git plumbing, zero config), WORKSPACE (viewing context: root dir + discovered repos incl. nested + conventions like the wt/ dir), CHANGESET (the review unit, keyed to repo + refs). **decided**
- **Review state keys on repo identity + changeset, NEVER on directory path.** The same PR review is the same review from any worktree of the repo. Multiple worktrees of one repo present as one repo with N checkouts, not N projects. **decided**
- Modes auto-detect: open a repo dir = project mode; open a dir containing repos = workspace mode. Optional committable workspace config file declares only what discovery cannot infer (where new worktrees are created, repos to surface/ignore, per-repo harness context docs). Config layering: app defaults, then workspace file, then repo file, then user overrides; the zero-config path never requires any file to exist. **decided**

### Home surface
- **All branches and PRs in one place** (Rai, 2026-08-04): a single view across the workspace showing repos, their branches, worktrees, and PRs with review state. This is the home/inbox surface, and it is the workspace/repo/worktree model made visible. **required**

Resolution with the legibility research: glass for chrome, sidebars, and overlay panels; code surfaces stay opaque high-contrast. **required**

## Lens Validation Synthesis (2026-08-04)

Three-way validation against real practitioner discourse: [[research/lens-validation-reddit|Reddit]] (~3,500 comments, 40 threads), [[research/lens-validation-hn|Hacker News]] (~15 major threads incl. every competitor launch), [[research/lens-validation-longform|long-form]] (blogs, studies, talks). All three verdicts agree in direction.

### Per-lens verdicts (three sources cross-checked)
- **Decision points: validated hard, strongest positioning fit.** Reddit wrote the thesis for us ("it feels less like reviewing and more like orbiting the decision"). Refinements that are now requirements: each decision must carry a reconstructed WHY (from plan/spec/ticket/session, marked as reconstructed) and everything needed to discharge it in place, else it is "a comment with better marketing"; hard visible ceiling on the count, the count IS the product.
- **Claims and evidence: validated, most distinctive, least occupied, zero conceptual opposition across ~5,000 comments.** Widen it: untested changes are the easy half; the documented failure is tests that pass and prove nothing (assertion-free, mock-only deltas, modified/deleted assertions, "rewrite tests until they pass", "paint a new target around the arrow"). The lens question is "would that test have failed". Make it bidirectional: every hunk maps to a requirement AND every claim to a test delta, with an explicit UNCLAIMED bucket that doubles as the scope-creep detector. Bonus: collapsing tests into evidence rows REDUCES review surface (reviewers admit they skim tests).
- **Blast radius: validated with native vocabulary and a credibility tax.** Build from cheap explainable signals: irreversibility, contract surface (schema, auth, public API, migrations), DELETIONS (heat models miss them), fan-in, CODEOWNERS overlap, and the SAFETY-NET-WEAKENING preset (test deletions/skips, new mocks on security paths, CI config changes, coverage threshold drops, lint disables, flag default flips: "any CI weakening is a hard stop"). Never churn-heat (anti-correlates with defects), never claim full impact analysis "or it reads as astrology".
- **Chapters (the sequence): mechanic validated, our fixed order contradicted, the word burned.** Three published expert orders exist (tests-first, CI-config-first, spine-of-the-change-first) plus the layering-vs-vertical-slice tension; ship ordering as named switchable strategies. Squash-merge culture destroys commit narratives, which validates post-hoc derivation. Anti-AI-prose backlash is loud: the sequence is ordering and boundaries, prose collapsed by default, never between reader and diff. Stage owns the word "chapter" and the single-sequence ground; sell ours as "the split you were about to demand, without the round trip".
- **Familiarity: cut from the set.** Blame decays in agent codebases ("git blame exists, and it won't say Claude"). Recast for phase 2 as PROVENANCE (how the change came to be: planned vs improvised, seen in earlier patchset, can the author answer for it) and/or expertise routing.

### Final proposed lens set v2 (awaiting Rai's ratification)
1. **The sequence** (sequence lens): post-hoc reading order, switchable strategies, prose collapsed. (Name TBD, "chapter" burned.)
2. **Decisions** (queue lens): the calls only you can make, with reconstructed why, capped count.
3. **Claims and evidence** (queue lens): bidirectional hunk-to-requirement and claim-to-test mapping with the unclaimed bucket.
4. **Subtraction** (queue lens, NEW): the delete queue. Merges Reddit's subtraction (over-engineering, "try-catch around a console.log", the 611-point "extremely over engineered slop is exhausting" complaint) + HN's defensive scaffolding (guard code that LOOKS like work) + redundancy against the existing repo ("40 lines doing what Array.prototype.map does"), which is invisible to diff-based cloud tools and only computable with the whole repo on disk: our structural advantage. The reviewer's real wish: not to understand the 3,000 lines but to be told which 2,000 shouldn't exist.
5. **Blast radius** (overlay lens): as corrected above, with security and safety-net presets.

Folded into the reading surface rather than a lens: **context reach** (the unchanged code a change implicates: "a large portion of lines I'm considering aren't part of the diff... almost every PR"; also the top criticism of Stage). Every chunk carries its implicated unchanged code (definitions, call sites, execution paths). Not a lens: performance (absent from discourse), dependency/supply-chain (preset on blast radius; "vibe-jacking").

### Promotions and demotions from validation
- **False-positive budget: candidate → CORE.** Quantified bot fatigue: "10-30 comments, 100% wrong" (CodeRabbit in the wild), "at least 75% off base" (Graphite), 80% noise consensus, uninstalls follow. Ship provenance labels, nit policy, one-click scoring from v1.
- **Harness disagreement: open question → recommend shipped feature** (see Open questions, with the stochasticity caveat).
- **Mobile: no organic demand signal** (six targeted Reddit searches, zero threads). Keep the paid companion but do not lead with it; revenue assumption has nothing behind it in this corpus.
- **Sequencing revision: the author side leads.** Three independent signals converge: branding (frequency builds habit), Reddit's most-upvoted process advice ("the proper place to introduce AI feedback is BEFORE the PR goes up"), and the moral refrain ("why should I bother to read something you didn't bother to write"). The earlier post-PR-first recommendation is revised: build the post-PR state/interop engineering regardless, but pre-PR self-review fronts the product.
- **The strategic reckoning:** the dominant Reddit moral position is that a large unread AI PR should be REFUSED, not accommodated. A tool that makes 3,000-line PRs pleasant risks reading as enabling the behaviour the community wants stopped. ~~The self-review route handoff is the product's alibi~~ (route handoff DESCOPED 2026-08-04; the positioning needs a replacement alibi — candidate: the author-side self-review mode itself, "review your agent's diff before it becomes anyone else's problem", without the shared-route artifact. Open for the synthesis pass.) Lead with making the author do the work, not making the reviewer heroic.

### Vocabulary from validation
- **"Chunk" is the unburned folk term** ("break it into reviewable chunks", "digestible"). "Chapter" burned (Stage), "lens" compromised (six tools as personas + one framework article). "Changeset" appears in public engineer usage, softening the internal-only rule. "Load-bearing" is native risk language. "Decisions" validated as the queue noun.
- Framings to steal: "guides my eyes", "return on attention", "judgment is the bottleneck", "the first human being to ever lay eyes on this code", "restore smell to the diff" ("a lot of generated code has no obvious smell" may be the best product framing found). Avoid "slop" in product voice: it insults the buyer's own output.
- Objections needing paragraph-one answers, confirmed: workflow-out-of-GitHub; AI-reviewing-AI circularity (answer: disagreement mechanic, human gate); "just prompt the model yourself" (answer: the product is the interface and the state model, not the inference; BYOK strengthens this objection so it must be answered, not dodged).
- Key numbers now in evidence: 93.4% of findings unique to one of four parallel reviewers; LinearB 8.1M PRs (AI PRs 2.6x bigger, pickup 5.3x slower, 30-day merge rate 84%→33%); agent duplication 1.87x human (p<0.001); agent test commits 36% mock-adding vs 26% human; moved/refactored code collapsed 21%→3.8% (GitClear).
