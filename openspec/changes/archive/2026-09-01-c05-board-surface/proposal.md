# C5 — Board surface: the lens board document, element registry, fold grammar, quote highlights, lens switcher (#489)

## Why

INVENTORY §3 carries 137 `[ws:C5]` claims — the biggest surface in the rebuild. It is the review's reading heart: a lens board rendered as a **document**, sections of typed elements in reading order, folding to their gists, threaded and highlighted, switchable across lenses and drillable across generations. C3 landed the frame that hosts it (`review-workspace-route.tsx` today renders an honest "being rebuilt" stub — B2 §489), C4 landed the shared review machinery every element renders through (`CodeBlock`, `CodeTabs`, `AnchorReveal`, `LineCommentEditor`, `ProseSelectionLayer`, `RichText`, `ReferenceChip`, the `citations.ts` span-read seam, and the extended `review` store slice with quote threads), and B3 froze the `LensBoard` projection shape (`packages/protocol/src/board/`). The board surface is the piece that turns all of that into the thing a reviewer reads.

The autopsy (S4, #489 comment 5431046732) named the spike's `lens-board.tsx` central defect: a **325-line `switch` over element kinds with a silent `default: return null`**. Add a `#462` kind and nothing renders it — no error, no warning, just a hole in the document. C5's spine is the fix: an **element registry**, one renderer per kind, `assertNever` on the default arm, so an unrendered kind is a **compile error**, not a silent omission. That inversion — from "forget to render a kind and lose it silently" to "forget to render a kind and the build fails" — is the reason this change exists rather than a straight JSX port.

## What Changes

All new work in `packages/app-ui/src/board/` (new), rendering the B3 `LensBoard` projection, composing C4's `review/` components, and reusing `packages/ui`'s `Collapse` primitive for the fold grammar. The client **never invents board shape locally** — every element it renders is a `HostElement` validated against `packages/protocol/src/board/schema.ts`; the projection is `LensBoardSchema`. **Zero new dependencies** (`lucide-react` for the per-kind glyphs is already an `app-ui` dependency).

- **`board/board-data.ts` — the board-fetch seam, one resolution point (mirrors C3's `sidebar-data.ts` and C4's `citations.ts`).** No `lensBoard`/`board` command is registered in the protocol yet — the `LensBoard` comment is explicit that "the command that returns it is B4/B10's business," and `packages/protocol/src/commands/index.ts` carries no such name. So `board-data.ts` is the ONE module that resolves a `LensBoard` for a `(generation, lens)` pair. Today it reads fixture boards delivered through the `MemoryBridge`/bridge context (fixtures arrive only through the bridge — the import fence, §13), validated against `LensBoardSchema`. When B4/B10 registers and binds the board command, `board-data.ts` is the only file that changes to a `useCommand(...)` read (Reconciliation 1). Every board-rendering path goes through it.
- **`board/registry.ts` + `board/kinds/*.tsx` — the element registry, one renderer per `#462` kind.** A `Record<HostKind, ElementRenderer>` map; the `Element` dispatcher looks up `element.kind` and renders, with an `assertNever(kind)` default arm so the map is **provably total** — adding a host kind without a renderer is a compile error (the named replacement for the spike's silent `default: return null`, autopsy S4). One small renderer file per kind under `board/kinds/`: `prose`, `callout`, `annotation`, `code_ref`, `finding`, `decision`, `requirement`, `noise_verdict`, `order_step`, `message`. Each ports the spike's per-kind JSX **through the fence** (spike is read-only reference; nothing under `board/` imports from `spikes/`), rewired onto the protocol `HostElement` shape and C4's `review/` components (`code_ref` → `AnchorReveal`/`useSpanRead`+`CodeBlock`; `message` → the thread exchange + optional anchor; prose everywhere → `RichText`). `round_outcome` and `review_comment` are the two host kinds C5's registry does **not** render — round report rendering is C9 ("it reuses this registry" — C9 widens the map) and the human GitHub `review_comment` belongs to the team-review surface (C7/C8). The registry's kind domain is therefore `Exclude<HostKind, "round_outcome" | "review_comment">`, keeping `assertNever` totality honest without a stub renderer (Reconciliation 3).
- **`board/section.tsx` — fold grammar + section rollups + delta marks.** A `Section` renders on `packages/ui`'s `Collapse`: folded, it is the `LensSection` projection's one-line `gist` plus its per-kind `counts`; unfolded, it is the referenced `section` element's children rendered through the registry. The disclosure pattern is the spike's (heading wraps the toggle button, both states stay mounted so fold/unfold animates). **Delta marks** (#486): a section carrying `delta: "new" | "reworked"` opens expanded and wears a **transient gold dot** (unread state, `bg-primary`); the dot clears when the reviewer interacts with the section (toggles or clicks the gist) and is replaced wholesale at the next regeneration. The viewed set that decays the mark is **UI-only** (the schema comment says so) — a new `board/viewed-delta.ts` store slice (`viewedDeltaSections` + `markDeltaViewed`), not persisted, not on the wire.
- **`board/board-view.tsx` — the `LensBoardView` document.** Assembles the sections in reading order under the board title, wrapped in C4's `ProseSelectionLayer` so a prose selection anywhere in the board raises the Comment/Explain/Request-Changes toolbar. `foldAll` starts every section folded except the Flagged lens (R44). This is the composition that reproduces the **Design and Findings board** reading experiences from the canonical `#462` kinds (Reconciliation 4 — the spike's four composite convenience kinds have no protocol home; their content is expressed through `section`/`prose`/`requirement`/`decision`).
- **`board/quote-highlight.tsx` — durable quote highlights + anchored threads (deferred from C4, Reconciliation 5).** C4's `rich-text.tsx` renders plain prose and explicitly left the `QuoteHighlight` durable-highlight overlay to C5 (C4 Reconciliation 7). C5 layers the highlight over every selectable `RichText` field: anchored quote ranges (from the `review` slice's `quoteThreads`, scoped by the protocol-shaped anchor identity — the target element id plus the board generation, finding 2, **not** bare anchor text) render as durable highlights over the prose; clicking a highlight opens a tooltip showing the thread's exchange (`messages`) with a reply input (`reviewActions.addQuoteReply`); overlapping highlights resolve to a readable stack. Refs live board-side (the anchor on the message/prose element); thread content is transcript-side (the `review` slice). An Explain thread (`kind: "explain"`) reads distinctly and never raises an exit count. **Fidelity ceiling (finding 6, honest-narrow fork b):** a paragraph that carries a highlight renders as plain interwoven text — bold, code spans, and citation chips **inside that one highlighted paragraph** are dropped, because the layer raw-slices the markdown string rather than interweaving through `RichText`'s private tokenizer. Anchor-free paragraphs render through `RichText` at full fidelity, so the loss is confined to the highlighted paragraph. Per Rai's fidelity ruling (styling is cheap; the token-aware interweave is the C14 A/B pass), C5 keeps the plain-text ceiling and this claim matches the code — it does **not** promise full-fidelity `RichText` inside a highlight.
- **`board/lens-switcher.tsx` — the lens segmented control, absent-not-disabled.** A segment per lens **that has a board** in the current generation (`generation.lensBoards` is a partial record — a lens with no board yields **no segment**, never a disabled one). Each segment carries a **delta rollup**: the count of `new`/`reworked` sections in that lens's board, shown as a small gold pip that clears as those sections are viewed (the section-level dot rolled up to the segment). Selecting a lens swaps the board through `board-data.ts`.
- **`board/generation-switcher.tsx` — generation drill-down to frozen drafts.** The generation model (#457, `session/model.ts`) is append-then-freeze: a live board and its frozen predecessors. A control drills from the current generation back to a frozen generation's boards (read-only), so the reviewer can read what a prior round showed. Resolves through `board-data.ts` with the target generation id.
- **`board/index.ts`** barrels the public surface (`LensBoardView`, the lens/generation switchers, the registry types) and `app-ui/src/index.ts` re-exports it; `review-workspace-route.tsx`'s stub is replaced by the mounted board surface.

## Reconciliations against main (packet drift, recorded per the dispatch rule)

1. **"The `LensBoard` projection via `useCommand`" — no board command is registered yet.** The packet says the board arrives "via `useCommand`", but `packages/protocol/src/commands/index.ts` registers no `lensBoard`/`board` command (only `patchset.readSpan` among the review commands), and `useCommand<K>` is typed over registered `CommandName` — it cannot name a command that does not exist. Registering that command is B4/B10's declared job (`lens-board.ts`: "the command that returns it is B4/B10's business"). So C5 isolates board-fetch behind `board/board-data.ts` (the packet's own "never invents board shape locally" discipline, one seam), fixture-backed through the bridge today; the live `useCommand` read is the single line that changes when B4/B10 lands — structured as the gated final cluster.
2. **`patchset.readSpan` is still contract-only.** `packages/server/src/dispatch.ts` still throws `"patchset.readSpan is not bound yet (B4/B10 bind dispatch)"`. Every code hydration on the board (a `code_ref` element, an `annotation`, a decision's evidence tabs) goes through C4's `review/citations.ts`, which already renders the honest `error` state until dispatch binds — C5 adds no new span-read path.
3. **The registry does not render `round_outcome` or `review_comment`.** Both are host kinds, but neither appears on a lens board: `round_outcome` is the round-report board (C9, which reuses and widens this registry) and `review_comment` is the human GitHub comment on the team-review surface (C7/C8). The registry's domain is `Exclude<HostKind, "round_outcome" | "review_comment">` so `assertNever` proves totality over exactly the kinds C5 renders, with no stub renderer standing in for absent work (no gates, no hollow passes).
4. **The spike's four composite element kinds have no protocol home.** The spike's `lens-data.ts` carries `spec-header`, `what-changes`, `capability-grid`, and `task-progress` as element kinds; the `#462` host schema collapsed these — they are not among the 13 canonical kinds. The protocol wins (packet: "the protocol wins on any divergence"). Their reading affordances are expressed through the canonical kinds in the Design-board **composition** (a spec header becomes a `section` title + `prose`; capabilities become `requirement` elements), not as new renderers. C5 renders the canonical vocabulary; the fixture boards arrange it.
5. **`QuoteHighlight` was deferred from C4 to C5 and is in scope here.** C4 Reconciliation 7 ported only `rich-text.tsx`'s base pipeline and named the durable quote-highlight overlay as `[ws:C5]`. C5 builds `board/quote-highlight.tsx` around C4's `RichText`, reading the `quoteThreads` shape C4 already extended the `review` slice to carry. It delegates to `RichText` verbatim for any paragraph with no anchor (full fidelity), and raw-slices only a paragraph that carries a highlight into plain interwoven text — the deliberate plain-text ceiling recorded on the bullet above (finding 6, fork b). It does not re-implement or replace `RichText`.
6. **The viewed-delta set is a new UI-only store slice, not read-state.** `canvas/read-state.ts` (#17) is a pure fold for path read-coverage and explicitly holds no view state; delta marks are a different axis (round `new`/`reworked` unread, per section, cleared on interaction, replaced each regeneration). C5 adds a small `board/viewed-delta.ts` slice for it, matching the schema's "the viewed set that decays the mark is UI-only".

## Review-fix ledger (PR #525 — dual review, all findings upheld)

Codex round-1 (4 P1 + 3 P2) and opus (P3s) reviewed the submitted branch; the orchestrator upheld every finding with zero Rule Zero drops. One finding carried an honest-narrow fork; the fork taken is recorded below.

- **A1 — Finding 1 (P1): board-data proves identity, not just shape.** `resolveBoard` took only raw data and validated shape, so a board returned for the WRONG `(generation, lens)` rendered as if it were the one asked for, and a parse failure rendered as "No board … yet" — a lie. `resolveBoard(raw, expected)` now returns a discriminated `valid | missing | invalid` union: a shape failure, a lens/generation mismatch (`reason: "identity"`), or an excluded kind (A4) each resolve `invalid`, rendered by `board-view.tsx` as a distinct honest `board-error` state, never as empty. Positive controls added for wrong-lens and wrong-generation.
- **A2 — Finding 2 (P1): quote highlights scoped by protocol-shaped anchor identity.** Matching was `text.includes(anchor)` review-wide — `quote_target`/generation identity ignored — so a span repeated across elements/lenses/generations (the fixtures' "Renewal was silent" in gen0 and gen1) painted every copy. `QuoteThread` now carries `target` (the element id, mirroring the `message` kind's `quote_target`) + `generation`; `addQuoteComment` takes that scope; the C4 selection toolbar reads it from the DOM (`data-element-id` + `data-generation`) at mint; the highlight layer matches only threads targeting THIS element in THIS generation. Applied to every selectable `RichText` field (prose/callout/finding/decision/annotation/requirement/noise_verdict), per the finding. **This required editing `review/selection-toolbar.tsx`, a C4 component the packet's Out-of-scope had listed "reused, not modified" — recorded here as the deliberate scope amendment the fix demanded (identity-scoping is born at the mint site).**
- **A3 — Finding 3 (P1): viewed-delta keyed by board, not the bare ref.** Section refs (`change`/`design`/`tasks`) repeat across generations, so keying the viewed set by the bare ref carried a reviewer's "seen it" into a same-ref reworked section of the next generation — falsely viewed. The key is now `boardId::ref` (`deltaKey`): a successor generation is a new board with a new `boardId`, so its delta sections start unviewed with no explicit reset.
- **A4 — Finding 4 (P1): excluded kinds rejected at the board-data boundary.** `LensBoardSchema` admits every host kind and the dispatcher returned `null` for `round_outcome`/`review_comment` — the spike's silent-hole defect still reachable. `resolveBoard` now rejects any board carrying an excluded kind as `invalid` (`reason: "excluded-kind"`); `Element` is narrowed to `ElementOf<BoardKind>` and `BoardElement` guards with a loud `assertExcludedKind` throw instead of the silent null. The registry test no longer enshrines the null. (Interlocks with A1: excluded = invalid data, rendered as the honest error state.)
- **A5 — Finding 5 (P2): board document subtree keyed by boardId.** gen0/gen1 reuse section refs, so without a board-identity key React reconciled the same-ref `Section` across a generation switch and kept the prior board's per-section fold `useState`. The `article` is now keyed by `board.boardId`, remounting the subtree on a board change. Positive control fails without the key.
- **A6 — Finding 6 (P2): fidelity ceiling — FORK (b) TAKEN.** The highlight layer raw-slices RichText, so bold/code/citations vanish inside a highlighted paragraph, while the proposal claimed the layer "wraps `RichText`". Per Rai's fidelity ruling (styling is cheap; the token-aware interweave is the C14 A/B pass), **fork (b) is taken: the recorded plain-text ceiling is KEPT and the proposal claim corrected** (What-Changes bullet + Reconciliation 5 above) so the ledger matches the code — not fork (a)'s token-aware rewrite. The code comment already stated the ceiling honestly; the proposal now agrees.
- **A7 — Finding 7 (P2): the two vacuous boundary tests are now positive controls.** The "round-trips" E2E only counted fixtures (never called the seam) — it now parses every fixture THROUGH `resolveBoard` under its requested identity and adds the wrong-lens/wrong-generation mutation cases (controls for A1). The selection-toolbar test seeded the store instead of selecting — it now drives a real selection → toolbar Comment → mint → highlight round-trip, asserting the minted thread carries the DOM-discovered scope (control for A2).
- **A8 — Finding 8 (P3): stale slice-count comment.** `store/index.ts` said "four slices — ui / review / run / signal"; it is five since C05 added `viewedDelta`. Comment corrected. (Opus P3s 2 and 3 were subsumed by findings 2 and 5.)
