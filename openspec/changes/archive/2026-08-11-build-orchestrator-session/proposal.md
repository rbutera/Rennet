## Why

Issue #12 shipped `canvasOps@2` — the versioned interaction + retrieval surface that is the orchestrator's entire tool world. What is still missing is the **session** that holds it: how the orchestrator wakes up oriented, taught to ask, and kept current as the user acts. Rai's superseding direction (voice, 2026-08-06, ~13:00) rejected both prior designs — a fat context dump and a capped primer — in favour of a third: **prime the orchestrator with a MAP of the review, not a container of it.** A lean, deterministic bootstrap says what exists and how to reach it; everything else lives behind the tools #12 already shipped.

The reframe is Rai's product thesis pointed inward. "Zoom in and out of the diff at any point" is the user-facing principle; `canvas.describe` at count → cohort → element depth is the same altitude ladder, machine-facing. The orchestrator does not carry a copy of the state — it carries orientation plus addressable access, and retrieval gets staleness for free (a call at minute 40 reads the current patchset; a primer assembled at minute 0 reads a memory of it).

Two properties this slice must make checkable, not hoped-for: **"the orchestrator is primed"** (a deterministic, versioned bootstrap whose digest lands in session provenance) and **"the shared state is inspectable"** (every user act pushed into the orchestrator's context is visible byte-for-byte in the open-assembled-prompt panel).

## What Changes

- Add the lean bootstrap to `packages/core` (`orchestrator-primer.ts`): a deterministic, versioned primer assembled as a **map** — B1 review identity + lineage + mode; B2 freshness verdicts (one line per repo, R30 at boot); B3 count-level canvas state (elements/cohorts/disposition-coverage/residue — **counts, never contents**; the decisions list is reachable, never inlined); B4 the **protocol card** (a versioned base instruction: the four-actor contract compressed, the two product principles [logical ordering, roll-up/zoom], what the orchestrator can never do, and the ask protocol — can-ask / how-to-ask / answer-shapes, including "never answer about the base branch or unexamined code from recall — retrieve or ask first"); B5 a tool index derived from the live `canvasOps@2` surface (names + when-to-use one-liners, schemas deferred); B6 the run-ledger headline. Assembly is a **pure function of state → bytes** (same state → same bytes), the card is a versioned constant matched against its template, and the primer's SHA-256 digest is recorded in the session's provenance. The whole primer is ≤ 4 KB.
- Add the context-update stream to `packages/core` (`context-update-stream.ts`): user acts pushed as structured events — `{selected}`, `{disposed}`, `{proposal-adjudicated}` (dismissals teach — outcome + edited payload), and `{viewing}` (cheap deixis). Per Rai's Q5 resolution, the user's **current canvas/lens/view context is injected at request time** with each ask, so the orchestrator resolves "this" without the user restating context. **⛔ No dwell/pace metrics** — not collected, not derivable. Every delivered event is appended to the byte-for-byte inspectable open-assembled-prompt log. **R35**: the stream is **not** an Rx pipeline — it consumes issue #10's post-commit `CanvasChangeFeed` plus direct user-act events in store/seq order; the `{viewing}` deixis batching is a **hand-rolled batcher under an injected clock** (bounded buffer, coalesce-by-key, **never silent** — a coalesced delivery states the seq range it covers). Consumers coalesce, never reorder.
- Add the session shell to `packages/core` (`orchestrator-session.ts`): `bootOrchestratorSession(inputs)` — ONE user-picked orchestrator harness+session, **fresh by default** (OQ9) — assembles the primer, records its digest in provenance, wires the stream, exposes the attached `canvasOps@2` tool surface (the structural actor partition: no user-only or engine-only op), the request builder (Q5 injection), and the open-assembled-prompt panel (primer + ordered event log).
- Add the attachment wiring to `packages/adapters` (`orchestrator-session-server.ts`): `attachOrchestratorSession(backend, inputs)` boots the core session **and** constructs the in-process `canvasOps@2` MCP server (#12's `createCanvasOpsServer`), returning both so a caller drops the server into `query()`'s `mcpServers` and the session into the conversation loop — the concrete "the orchestrator session attaches canvasOps@2".

## Capabilities

### New Capabilities

- `orchestrator-session`: the lean map-not-container bootstrap (B1–B6, ≤ 4 KB, deterministic, versioned, digest-in-provenance), the versioned protocol card that teaches the orchestrator to ask, the context-update stream (structured user-act events, hand-rolled deixis batcher under an injected clock, change-feed consumption in seq order, request-time view injection, byte-inspectable open-assembled-prompt panel), the fresh-by-default session shell that attaches the live `canvasOps@2` surface, and the adapter that constructs the in-process MCP server alongside the session.

## Impact

- Adds `packages/core/src/orchestrator-primer.ts`, `context-update-stream.ts`, `orchestrator-session.ts` (re-exported from `core/index.ts`, colocated-tested) and `packages/adapters/src/orchestrator-session-server.ts` (re-exported from `adapters/index.ts`, colocated-tested). No new package; no new external dependency (SDK + Zod already deps of `adapters`, the node-free `sha256Hex` already in `protocol`); no dependency-arrow change — architecture and licenses gates untouched.
- Consumes, does not change, #12's `canvasOps@2` and #10's `CanvasChangeFeed`. The tool index is derived from the live `CANVAS_OPS_TOOLS` registry (picks up #49 item 3: the attached surface is asserted to be exactly the canvasOps@2 registry and to contain no user-only/engine-only op).
- Deferred to follow-ups: the `context.*` retrieval bucket (base-branch context issue); the async `context.ask` ticket path; the E1–E5 empirical primer/ask experiments; #54's deferred L3 canvas-op persistence (out of scope here — this slice reads the surface, it does not persist L3).
