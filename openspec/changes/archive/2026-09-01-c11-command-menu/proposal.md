# C11 — Command menu: ⌘P/⌘K, the six keybindings, remapping, one global key owner (#489)

## Why

INVENTORY §9 carries 13 `[ws:C11]` claims for the command menu (a modal, fuzzy-filtered, arrow-navigable command dialog toggled by `⌘P`/`Ctrl+P`, entries for sessions, projects, settings pages, and actions, an empty state, open-state in the store), and §14 items 1/5/6 record four keybinding debts on the same surface: the six advertised binds are unwired (§14 item 1), the spec-header's raw `⌘R` control must die and join no registry (R69), and keybind remapping is unbuilt (R70). C3 deleted the legacy palette and `command/commands.ts`'s Surface-coupled commands in the delete-first cutover, keeping only the pure keybinding helpers, and recorded (reconciliation 4b) that "keyboard dispatch and the palette go dark until C11 rebuilds ⌘K on B10's registry." So today the running router app has **no command menu** and **no key dispatch at all** (`routes/app.tsx` binds no `keydown`), while the sidebar's Search row and rail button already flip `ui.commandMenuOpen` (C3 reconciliation 6) against a menu that nothing renders — an advertised affordance with no surface behind it. C11 builds that surface, wires the six keybindings through **one** global key owner with a priority stack (replacing the spike's scattered hand-rolled Escape listeners, autopsy S7), and builds remapping.

The menu is one of the command registry's three readers (#465): the sidebar, the ⌘K menu, and the orchestrator's app tools all read the one `commands` table; the menu contributes no list of its own for registry commands — it filters the table by `exposure.commandMenu` and derives each label from the command id (R4). Its other entries (sessions, projects, settings pages, actions) are **navigation**, sourced from the same projections the sidebar reads, not from the registry.

## What Changes

All in `packages/app-ui`, on C1's seams (`data/`, `store/ui.ts`, `routes/`), C2's `Command` primitive (`@rennet/ui`, already proven by C3's new-chat picker), C3's shell (`shell/`, `shell/sidebar-data.ts`), and the keybinding helpers C3 kept in `command/commands.ts`. **Zero new dependencies** (`cmdk` rides in through `@rennet/ui`'s `Command`; the keybinding helpers already exist).

- **`shell/key-owner.tsx` — the ONE global key owner (autopsy S7).** A single window-level `keydown` listener, mounted once by the frame, that owns app-level key dispatch and a **priority stack** for Escape. Overlays register a layer (`useKeyLayer`) with a priority; the highest live layer gets first refusal on a key. Escape resolves top-down: the frontmost open dialog (`ui.openDialogs`, already a stack) consumes it, then the command menu (`ui.commandMenuOpen`), then any registered layer, then no-op — deterministic, one owner, no racing listeners. This replaces the pattern the spike hand-rolled in six-plus shell surfaces (autopsy S7); the app-level Escape consumers that exist in `app-ui` today adopt the layer API, and C5/C12's later overlays register the same way when they land (the API is the standing replacement, not a one-off migration).
- **`shell/command-menu.tsx` — the ⌘P/⌘K menu (INVENTORY §9).** A `@rennet/ui` `Command` dialog controlled by `ui.commandMenuOpen`, with cmdk's fuzzy filter, ↑/↓ navigation, Enter to run, and Escape to close (through the key owner, not a private listener). Every entry shows its group name beside its title; an empty result states that no commands match. `⌘P` opens it **search-first** and `⌘K` **command-first** — the one dialog, two entry modes (a small `commandMenuMode` slice field, reconciliation 1). The sidebar Search row and rail button already open it (C3); the frame now renders it once.
- **Menu entries — projections for navigation, the registry for commands.**
  - *Navigation (projections):* sessions (title, with project + host as extra keywords, archived excluded, running one opens the chat and routes to it), per-project "<project> — Context Map" and "New Chat in <project>", the four settings pages (Environments, Appearance, Keyboard Shortcuts, Projects), and the Add Project / Add Environment action entries (`uiActions.openDialog`, matching C3's sidebar). Sessions come through C3's `shell/sidebar-data.ts` seam (the same projection the tree reads — one source, MemoryBridge-stubbed until B9, live when B9 lands), never a second query.
  - *Registry commands (R4):* the menu filters `commands` (`@rennet/protocol`) by `exposure.commandMenu === true` and renders each surviving row with a label **derived from its id**. Today every row initializes `commandMenu: false` (reconciliation 2), so this channel renders nothing yet — honestly empty, not fabricated. Flipping the flags is B10/registry work (out of scope); C11 builds the reader + the id→label mapping and proves it against a fixture registry, so a flipped row appears the instant B10 flips it.
- **The six keybindings through the key owner (§14 item 1).** The spike's `settings-data.ts` advertises six binds — `search` `⌘P`, `commands` `⌘K`, `new-chat` `⌘N`, `toggle-sidebar` `⌘B`, `toggle-chat` `⌘J`, `settings` `⌘,` — of which only `⌘P` is bound today, and by an ad-hoc listener at that. C11 gives all six one home: the key owner matches each through its **effective** binding (catalogue default overlaid by the user's override, via `command/commands.ts`'s `effectiveKeybinding`/`matchKeybinding`) and runs the action — `⌘P`/`⌘K` open the menu (search/command mode), `⌘N` opens new-chat (`openDialog`), `⌘B` `toggleSidebar`, `⌘J` toggles `chatOpen`, `⌘,` routes to settings. `⌘P`'s ad-hoc listener is re-homed here, so no chord is bound twice.
- **Kill raw `⌘R` (R69) — the registry half.** `⌘R` joins no catalogue and the key owner never binds it, so the app never hijacks the reload chord; the Keyboard Shortcuts page advertises no reload row. (The spec-header control that issued the raw reload lives in `lens-board.tsx` and is C5's to delete — reconciliation 4; C11 owns "its chord joins no registry.")
- **Keybind remapping (R70/#492).** The Keyboard Shortcuts settings page's per-row "Change" performs real remapping: enter a capture mode, read the next chord, surface a conflict inline when the chord already belongs to another row (**disclosed, never blocked** — Rule Zero), and persist the override. Persistence rides the **already-landed** `settings.setKeybinding` command (which `settings-screen.tsx` already consumes via `KeybindingOverrides`); the key owner reads the effective binding, so a remapped action fires on the new chord after a reload (overrides load on boot through `settings.get`). Reconciliation 3 records that the packet and spike name this store "client-settings.json" while the landed command writes `~/.rennet/config.json` — C11 persists through the landed command rather than inventing a second file.

## Reconciliations against main (packet drift, recorded per the dispatch rule)

1. **The `ui` slice needs a `commandMenuMode`.** C1/C3 landed `commandMenuOpen` + `setCommandMenuOpen` but no mode. `⌘P` (search-first) and `⌘K` (command-first) open the same dialog with a different default view, so the slice gains `commandMenuMode: "search" | "command"` (default "search") and `setCommandMenuOpen` takes an optional mode. Every existing caller (the sidebar Search row) stays valid — an omitted mode is "search". A minimal in-place extension, mirroring C4's reconciliation-1 pattern.
2. **No registry row carries `exposure.commandMenu: true` today.** `packages/protocol/src/commands/index.ts` initializes every row `commandMenu: false` (verified at HEAD; the `CommandExposure` type and the flag exist, but flipping rows is the registry's own work). So the registry-command channel renders **nothing** now — correct and honest, not a bug. C11 builds the reader and the id→label mapping and tests them against a fixture registry with a `commandMenu: true` row; the live rows arrive when B10 flips flags. The menu never fabricates a command entry.
3. **Remapping persists through `settings.setKeybinding` (`~/.rennet/config.json`), not a new `client-settings.json`.** R70/#476 and the spike's `settings-data.ts` comment say "persist to client settings / `~/.rennet/client-settings.json`," but the landed `settings.setKeybinding` command writes `~/.rennet/config.json` and `settings-screen.tsx` already round-trips `KeybindingOverrides` through it. C11 reuses that path (the cited-source reality) rather than adding a second persistence file — inventing one would duplicate machinery and contradict a landed command. The naming gap is flagged, not resolved by new scope.
4. **R69's control deletion is C5's; C11 owns R69's registry half.** §14 item 5 tags the raw-`⌘R` spec-header control `[ws:C5]` (`lens-board.tsx`), and the packet's C11 objective says "kill raw ⌘R (R69)." The half C11 owns is the keybinding registry: `⌘R` binds to nothing and appears in no shortcuts row, so the chord "joins no registry." Deleting the on-screen control in the spec header travels with C5's board rebuild.
5. **The command menu and key owner live under `shell/`.** C3 established `shell/` for frame chrome (`top-bar`, `trail`, `sidebar/`); the menu and key owner are frame chrome and follow the convention. The keybinding **helpers** (`effectiveKeybinding`, `matchKeybinding`, `formatKeybinding`, `KeybindingOverrides`) stay where C3 kept them (`command/commands.ts`) and are imported, not duplicated.
6. **Live registry-command execution is deferred to B10, but the mechanism is built + tested now.** Selecting a registry-command entry dispatches through the bridge (`useMutation`); most registry commands are contract-only until B10 binds dispatch, and no row is flagged `commandMenu: true` until then. So the packet's "⌘K executes a registry command end-to-end" proof runs over `MemoryBridge` (a handler for a fixture `commandMenu: true` command), proving the whole path now; the deferred part is B10 flipping real flags and binding live dispatch — isolated in the final cluster, never a hollow pass.
