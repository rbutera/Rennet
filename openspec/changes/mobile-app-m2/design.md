# Design — mobile-app-m2

## Context

M1 shipped the reading phone; M0 shipped the runtime. Everything M2 acts through already exists on the daemon: the streaming `review.ask` lifecycle (raises/clears attention), `review.reattach`, the publish engine (`publish.requestConsent` → `publish.review` / `publish.submitPr`, idempotent, "what you preview is what posts"), `review.openPr` / `review.capture` kickoff, and `review.handoff.run`. The desktop conversation UI (`packages/ui` conversation-host) is the behavioral reference for stream rendering — not a code source (DOM-bound). Wireframes 20/22/23 fix the screens; the ideation taxonomy fixes push behavior. The paper/signing metaphor is dead: preview → post, no ceremony.

## Goals / Non-Goals

**Goals:**

- The phone acts: watch, steer-adjacent answering, stop, post, kick off — every action riding existing commands.
- Shade answering that is trustworthy: exactly-once delivery semantics from a notification action, truthful failure.
- All six attention families live; the taxonomy's seams close.

**Non-Goals:**

- No general steering composer beyond the ask reply (free-form mid-turn steering of arbitrary turns is desktop parity work, not M2 acceptance).
- No voice input; no widgets/live activities; no store distribution (M3).
- No new protocol commands unless the shade-action payload genuinely needs one field (additive only).

## Decisions

1. **Turn screen = reattach paint + live stream.** Enter → `review.reattach` renders persisted thread state; the supervisor's `onAskStream` subscription (rebind-safe) appends live events. Timeline is a virtualized list reusing M1's canvas-row discipline; return-to-tail is a scroll-anchor state, Stop maps to the existing interrupt path of the streaming ask lifecycle.

   **Finding A (interrupt) — ruling: any authorized socket may interrupt; the outcome is persisted; Stop tells the truth.** No ownership check gates `review.interrupt` (Rule Zero) — any authorized socket may stop a review's in-flight turn. The interrupted outcome LANDS IN THE PERSISTED THREAD MESSAGES: the ask lifecycle's abort guard keeps the `streaming` placeholder on disk, the thread store's crash-recovery transform reads it back as `interrupted`, and `review.reattach` returns it in `threads` with `inFlight` empty — never a turn hung forever in-flight (asserted end-to-end against a real `FileThreadStore` in `dispatch.test.ts`). Against a **pre-M2 daemon** that lacks `review.interrupt`, Stop must LOOK disabled (truthful), not silently no-op: the daemon advertises an `act` handshake feature (`serverInfo.features.act`, additive/COMPAT) when it wires the M2 acting seams; the phone reads `supervisor.actAdvertised()` and renders Stop visibly disabled ("update daemon") when it is absent.
2. **One reply shape.** Chips and free text compose client-side into the single `review.ask` reply string (chip label + newline + direction, matching how the desktop composes decisions with context). Send-mode (interrupt vs queue) uses the M0 supervisor's invoke semantics; drafts persist in AsyncStorage per review.
3. **Shade actions ride the push payload.** The ask push already carries substance; it gains the chip descriptors (additive field on the existing push payload — no new command). The app registers a notification category per ask push; the OS action handler posts the same `review.ask` reply through a background-capable path (Expo notification response in a headless task where the platform allows; where background execution is denied, the action opens the app pre-filled and sends immediately — still one tap, disclosed in the guide). Exactly-once: the reply carries the ask's turn id; the daemon's existing superseded-turn refusal is the dedup, and a refusal surfaces as the truthful failed-answer notification update.

   **Finding B (shade actions) — ruling: absent actions lose nothing; the schema discipline holds.** The `actions` field is optional and MEANS a quick-answer affordance ON TOP of a full ask push — never a precondition for it. An ask with no chips (today's real asks) still renders a useful shade notification: the question as the body, a body-tap that deep-links into the ask, and the in-app free-text answer path — a chip is never fabricated to fill the gap (`shadeActionsFor(undefined) ⇒ []`, tested). The M1 schema-refinement discipline applies: `attentionActionSchema` pins `id` and `label` to `z.string().min(1)` so an action, when present, is never empty-id/empty-label.
4. **Publish flow is three screens, zero ceremony.** Preview renders the composed outbound review (the same payload bytes the engine will verify), post taps `publish.requestConsent` + the destination command; the posted screen shows the returned URL. Idempotency is the engine's (consent key + head-branch idempotence) — the app adds nothing. "Ask for changes" starts a refine turn and lands on the turn screen.

   **Finding C (composition boundary) — ruling (a): BOTH loops end on the phone.** The phone cannot compose the byte-exact outbound payload: the editable collation model lives in the DOM `ui` layer, off-limits to the mobile boundary, and `layer:ui` may not import `layer:core` (`eslint.config.mjs:57`), so the ruling's literal "relocate composition to core + ui re-export shims" is architecturally impossible (it would invert the layer graph). It is also unnecessary: `@rennet/core` ALREADY owns the postable-bytes composition (`canonicalReviewPayload`, `deriveReviewEvent`, `canonicalPrSubmissionPayload`), pinned byte-exact to the ui twin. What was ui-only is the *editable* collation model (reword/merge/split/reorder), which by this decision the phone never uses. So the boundary-legal resolution: the **daemon** composes (it is `layer:server`, which imports core), via one new node-free core function `reviewCommentsFromDispositions(dispositions)` that maps the review's stored dispositions to the default (unedited) comments. `publish.compose {commandId, reviewId, mode}` returns — mode `"review"`: `{comments, payload, verdict, destination, title}` for a team-PR post via `publish.review`; mode `"pr"`: `{submission, payload, …}` for an own-branch open via `publish.submitPr`. The phone previews AND posts exactly those bytes, and `publish.review`/`publish.submitPr` re-verify their own core bytes — "what you preview is what posts" holds one-source across shells. **No `ui` file is touched** (smaller conflict surface than shims, and no layer violation); the desktop keeps its pinned twin. A pre-M2 daemon does not implement `publish.compose`; the phone's publish surface says the daemon needs updating (truthful, like Stop), never a dead post button. COMPAT-tagged additive.
5. **Share sheet via Expo intent/config plugin** (Android intent filter + iOS share extension through the config plugin route); shared URL lands on the kickoff screen with the link applied. If the iOS share-extension plugin proves disproportionate this pass, Android intent + iOS universal-link paste path ship and the extension is a recorded follow-up — the acceptance keeps "share a PR URL to Rennet" on at least one platform and paste-everywhere.
6. **Family wiring:** handoff-completed raises where `review.handoff.run` resolves its outcome; publish-ready raises where the composed draft first becomes ready (the same dispatch point the desktop uses to enable its post survace), clears on post or on preview view per the clear-on-view rule.
7. **M1 cut closures:** proposal adjudication wires `canvas.adjudicateProposal` with the proposal ids the canvas payload carries; digest counts derive from the projected canvas/delta payloads client-side (no new protocol); cohort grouping folds the canvas rows under cohort headers with judged-collapse.

## Risks / Trade-offs

- **Background notification actions are platform-fickle** (iOS background execution limits). Mitigated by the decision-3 fallback (action opens app pre-filled + auto-send) and by the truthful failed-answer update — never a silently dropped answer.
- **Share-extension packaging friction on iOS** — mitigated by decision 5's staged fallback, recorded honestly.
- **Answer/turn races** (turn completes while the shade answer is in flight): the daemon's superseded-turn refusal is authoritative; the app/notification always reflects the refusal rather than pretending the answer landed.
- **Scope**: publish-ready raise point must not entangle with the publish engine's consent internals — it raises on readiness state, reads nothing secret, changes no egress semantics.

## Codex review hardening (findings 1–11)

A Codex review of the M2 acting seams raised eleven findings; all accepted, with finding 3 re-shaped by the lead. Resolutions as landed:

1. **Preview shows everything that posts** — the publish preview renders every review comment in full (path, line, side, type, body) and the whole PR (title, base ← head, draft flag, full body), not a "N comments collated" summary. The data already flowed from `publish.compose`; the preview now shows it, honouring "what you preview is what posts".
2. **Bound compose artifact** — `publish.compose` returns a deterministic `compositionId` over (reviewId, active patchset, mode, canonical payload). `publish.requestConsent`/`review`/`submitPr` recompute it from the CURRENT review and refuse a cross-review or stale-revision post (review-mode re-derives from current dispositions, catching a disposition edit that landed between preview and post). Pure integrity, no ceremony; optional/additive so the desktop's local-compose path is untouched. `publish.tsx` also resets `composed`/`posting` on every route change so the previous review's preview never flashes.
3. **Shade answers bind to the attention item id** (re-shaped) — the ask push carries its attention id; a chip-tap invokes `review.ask` with it, and the daemon consumes that attention atomically (before the first await) as the turn's dedup. Duplicate tap ⇒ truthful "already answered"; forged/stale id ⇒ refused (no active item). No new ask machinery — it reuses the attention registry's active set. The app parses the untrusted push payload (`parseAttentionPushData`), never a blind cast.
4. **Background action handling** — the routing dedups a replayed cold-start response (no re-send on remount) and, on a failed shade answer, updates the notification to "answer didn't land" before deep-linking. True background-terminated action handling is wired via `expo-task-manager` (`~55.0.18`, SDK-matched, admitted by the lead): a module-scope `TaskManager.defineTask` (defined + registered at `index.ts` entry) answers a chip tap on **Android** while the app is backgrounded/terminated — it reconstructs the send headless (persisted daemon list + keychain token + one short-lived `WsRennetBridge`, the same `askReplyInvoke` bytes the in-app card sends) and, on failure, schedules the truthful "answer didn't land" notification. On Android the ask category is registered background-capable (`opensAppToForeground: false`); on iOS — no background action-tap task — the action opens the app pre-filled and the deduped cold/warm handler sends (still one tap), the honest fallback the platform forces, never a dropped answer.
5. **Reattach real in-flight + delta dedup** — the live-turn registry tracks each streaming turn's coalesced body, and `review.reattach` reports genuinely-live turns as real `inFlight` state (dropping the interrupted placeholder for a turn still live) instead of the crash-recovery transform painting a running turn as stopped. Every ask-stream event carries a per-review monotonic `seq` (additive, stamped at the ws broadcast choke point); the reducer rejects an already-applied seq per entry, so a re-delivered `ask-delta` never appends twice, and a per-turn seq space keeps a daemon restart from freezing the stream.
6. **One terminal event on interrupt** — an aborted turn emits exactly one terminal stream event: `ask-complete` is skipped when the controller was aborted, so a killed turn never flashes a completed answer before `ask-interrupted`. The aborted branch (swallowed-return and abort-then-throw alike) persists an explicit `interrupted` replacement carrying the partial streamed body, so the turn survives a store reload as interrupted directly.
7. **No cross-turn abort** — `LiveTurnRegistry.register` rejects a duplicate live id rather than silently replacing the prior controller (a `Map` holds one controller per id; a silent replace would orphan turn A and let a Stop aimed at B reach A). A sequential reuse after settle is fine.
8. **Path safety** — comment/disposition paths are validated repo-relative with no traversal at BOTH ingestion (`review.setDisposition`/`canvas.disposition`) AND compose (`publish.compose`), via a node-free `isRepoRelativePath` in core. Projected `rpcError`s redact absolute paths a root/home substitution missed, so a raw host path never reaches a projected client.
9. **Safe repo matching** — kickoff repo matching prefers an exact `owner/repo` and uses a bare repo name only when unique, so a fork and its upstream never route a PR to the wrong clone. Reading Android `Intent.EXTRA_TEXT` is wired via `expo-share-intent` (`6.1.1`, MIT, SDK-55 line, admitted + vetted by the lead): its config plugin (Android-only — `disableIOS: true`, `androidIntentFilters: ["text/*"]`) generates the SEND intent filter and its native module reads the shared text, which `useShareIntentRouting` extracts (pure `sharedUrlFromIntent`) and routes to `/kickoff?url=…` for `parsePrRef` to validate. The hand-rolled `android.intentFilters` that read nothing is removed — the plugin now owns a single, honest filter. iOS keeps the paste + `rennet://kickoff` paths; the iOS share extension stays the recorded follow-up (design decision 5), not a manifest that lies about an iOS share sheet.
10. **Precise attention acks** — clear-on-view acknowledges the EXACT attention id for the landing surface (turn → ask-pending, digest → review-finished, error → turn-failed), not the whole review's families; the publish preview clears publish-ready only after its own compose re-raises it. The daemon suppresses a redundant broadcast + push when an identical item merely refreshes (`raiseIfChanged`).
11. **Refined attention schema** — `actions` are valid only on an ask-pending item, bounded in count (≤4) and id/label length, with unique ids; a malformed item is rejected at parse, in the wire decoder and in the app, so no fabricated or ambiguous chip is ever rendered.

**Dependency decisions (admitted by the lead, vetted per the Dependency Standard):** finding 4's background-terminated action handling is wired via `expo-task-manager` (`~55.0.18`, first-party Expo, SDK-matched); finding 9's `Intent.EXTRA_TEXT` read is wired via `expo-share-intent` (`6.1.1`, MIT, SDK-55 line, Android-only plugin — the iOS share extension stays the recorded follow-up). Both are recorded in the [dependency standard](/developing/reference/dependency-standard/). All eleven findings are landed and gated.
