## Why

Dispositions are path-grained. `DispositionAnchor = {path, contentDigest}` (`@rennet/types`) attaches a reviewer action to a whole file; the user cannot dispose at a line or span. Two independent reads (issue #78; canvas-not-viewer audit 2026-08-07) converge on the same kicker: **#21's GitHub publish pipeline REQUIRES `line`/`side` review threads** (its body forbids `position`), so path-grained dispositions literally cannot feed the destination. The inhabited canvas (dispositions at spans) and the publish destination need the SAME missing plumbing — the strongest build-sequencing argument in the queue.

This is the **keystone**: #78 sets the line/span payload contract that BOTH #22 (publish sheet) and #21 (GitHub publish) consume. Build it once here, or they build it twice.

Rai's #48 ruling (voice, 2026-08-08) fixes the carry rule this touches: successor carry is **not** a mechanical approved-only vs any-byte-identical binary. Byte-identical is the deterministic FLOOR / fast path; above it, a **medium-tier model** judges whether a prior disposition is still RELEVANT to the re-captured code. So span-grained carry = a cheap deterministic byte-identical floor PLUS a call to a new **disposition-relevance-judge** Model Council job. The floor stays pure and red-provable; the model call is mocked in CI.

## What Changes

- **Span anchor (additive, backward-compatible).** `DispositionAnchor` gains OPTIONAL `span` (1-based file-line range), `side` (additions/deletions/context), and `spanDigest` (byte digest of the span's side-text at authoring time). Presence of all three ⟺ the disposition is span-grained; absence ⟺ path-grained (unchanged). File-line + side is registrar-independent, so the data model **sidesteps #84** (the CodeView's positional occurrence map) at the carry/payload layer.
- **Fold identity by full anchor.** `DispositionSet` dedup and `DispositionCleared` key off the full anchor identity (`anchorKey` = `path` or `path#Lx-Ly@side`), not bare `path`, so two spans on one file (and a path-grained + a span disposition on the same file) coexist and clear independently. `DispositionCleared` carries the anchor key.
- **Span-grained carry (the deterministic floor).** `carryDispositions` extends fail-closed to spans: a path-grained disposition carries iff its file is byte-identical (unchanged); a span-grained disposition carries iff the successor file's side-text at the SAME file-line span is byte-identical to `spanDigest` and in bounds. Any change, shift, out-of-bounds, missing side, or missing file → dropped (the reviewer must re-read). No fuzzy matching — that is the judge's job.
- **The relevance judge (Rai #48 ruling).** A `DispositionRelevanceJudge` port + pure `partitionCarry` (floor → `{carried, candidates}`), `applyRelevanceVerdicts` (canned verdicts → re-anchored carries, fail-closed on an out-of-bounds re-anchor), and `carryWithRelevance(previous, next, judge)` composing floor → judge-on-candidates → apply. A `ReviewService.recaptureWithRelevance` async entrypoint wires it live (emits `PatchsetActivated` + a `DispositionsCarried` re-attach event); the default `capture()` path keeps the pure floor only, so nothing existing regresses. The judge is a port — CI injects a deterministic stub, the model never runs.
- **The council job.** `disposition-relevance-judge` registered in `JOB_CATALOGUE` (light tier — bounded inference, sibling to `disposition-triage`; the "medium model" the ruling names is the effort knob, exactly how `disposition-triage` is Luna-medium) with entries in all three assignment tables (Luna-medium / Haiku-low / Luna-medium). Routed via the existing `resolveAssignment` council path (#69/#81); the live budget gate applies. Documented in `docs/Rennet Model Council.md`.
- **The publish payload contract (#22/#21).** A pure `toPublishThread(disposition)` mapping a disposition to the GitHub review-thread shape `{path, line?, startLine?, side?: "LEFT"|"RIGHT", body, type}`: a span disposition → `line`/`side` (deletions→LEFT, additions/context→RIGHT; multi-line → `startLine`+`line`); a path disposition → a file-level comment (no line). This is the single line/side contract #22 and #21 build on once.

## Capabilities

### New Capabilities

- `span-grained-dispositions`: the span anchor (file-line + side + spanDigest, additive), full-anchor fold identity, span-aware byte-identical carry (the deterministic floor), the disposition-relevance-judge port + council job + `carryWithRelevance` (floor + model relevance judgment above it), and the `toPublishThread` line/side publish contract feedable to #21.

## Impact

- `packages/types/src/index.ts`: extend `DispositionAnchor`; add `DispositionRelevanceJudge`/`RelevanceCandidate`/`RelevanceVerdict`, `PublishThread`, `DispositionsCarried` event field types. `packages/protocol/src/index.ts`: extend `dispositionAnchorSchema` (optional span/side/spanDigest with a presence-coupling refinement). `packages/core/src/index.ts`: span-aware `carryDispositions`, `anchorKey`, full-anchor fold, `extractSpanText`, `partitionCarry`, `applyRelevanceVerdicts`, `carryWithRelevance`, `toPublishThread`, `recaptureWithRelevance` + `DispositionsCarried` event; span-aware `setDisposition`. `packages/core/src/model-council.ts`: the new job + three table entries. No new package, no dependency-arrow change, no UI change (the CodeView span-selection authoring surface is #77-area and out of scope). The architecture and licenses gates are untouched.
- **#84 named, not deepened.** Span AUTHORING via the CodeView inherits #84's latent positional-occurrence fragility (a span selected on an oversize-split fragment may resolve the wrong occurrence). The #78 data model deliberately anchors by **file line + side, registrar-independent**, so carry and the publish payload do NOT go through the positional occurrence map and add no new positional assumption. #78 does not deepen #84; the authoring conversion is a UI concern tracked by #84.
- **Read-set derivation unchanged.** Every disposition still carries `anchor.path`, so the file-level read-set (`disps.map(d => d.anchor.path)`) in `canvas.ts`/`canvas-ops.ts`/`orchestrator-primer.ts` keeps working with zero change.
- Compatible with the parallel collation-draft-canvas reshape (R40): span-grained dispositions are the *granularity* of items that will live in the editable draft. This change is the data model + carry logic only — NOT the collation UI.
