# C6 — Diff view: the raw-patchset surface in GitHub's Files-changed shape (#489)

## Why

INVENTORY §4 carries 28 `[ws:C6]` claims describing the raw-diff surface — the `?view=diff` alternative to the board: a left-hand file tree + filter, per-file diff cards with dual old/new line-number gutters, hunk headers, GitHub's five-square add/delete proportion chip, viewed-tracking (checkbox + `n / m viewed` count, collapse-on-viewed), filename deep-links (`?view=diff&file=<path>` jumps to and scrolls a file's card), and the SAME line-comment / Request-Changes machinery every other code surface uses — so a comment left on a diff line is the identical object a comment left on a board excerpt is. The pill that reaches it (`History · Map · Diff`) already ships in C3's `shell/top-bar.tsx`, toggling `?view` through the C01 query grammar; today selecting **Diff** lands on the B2 review-workspace stub because no surface renders it yet.

The spike's `components/diff-view.tsx` is one of its cleanest files (autopsy: "port under review"): the presentation — file tree, cards, gutters, `StatSquares`, viewed collapse — is sound and travels almost verbatim. Only two seams are rewritten, exactly as the packet directs:

1. **The fixture seam.** The spike imports a static `diffFiles` array from `lib/diff-data.ts` and renders its pre-parsed `DiffHunk`/`DiffLine` shape. The real surface reads the **patchset projection** — the active patchset's `files[]` (`PatchFile`: `path`, `previousPath`, `status`, `additions`, `deletions`, `binary`, `patch`) — which arrives through `useCommand`. `PatchFile.patch` is raw unified-diff text, not the spike's pre-structured hunks, so the port parses it into hunks/lines through the repo's existing `@@` grammar rather than re-importing a fixture.
2. **The comment seam.** The spike's `DiffHunkView` reads `useCodeComments()` — the dead `CodeCommentsProvider` shim with its `store?.` phantom guards (autopsy S3, fence rule 4). C4 already retired that: `review/line-comment-editor.tsx` is the one editor and the `review` store slice is the one home for line comments. The diff's line-comment button opens **C4's `LineCommentEditor`** and writes the **`review` slice** directly — `setCodeComment`/`clearCodeComment`/`stageAsk`, read via `selectCodeComments` — the SAME wiring `review/code-block.tsx` already ships. That is what makes a diff-line comment and a board-excerpt comment the identical `review.codeComments[path][line]` object.

Leaf components also lose their `next/navigation` imports (fence rule 3): the spike reads the deep-link file param with `useSearchParams`; the port reads it through wouter's `useSearch` and the C01 `routes/url.ts` query grammar (`readSessionQuery().file`).

C6 delivers the diff surface and mounts it for `?view=diff`. It does **not** touch the board (C5) or exits/staging (C8).

## What Changes

All in `packages/app-ui/src/review/` (new files) plus a minimal `?view` switch in the review-workspace route. **Zero new dependencies**: `lucide-react`, `shiki` types, and `@rennet/ui`'s `cn` are already `app-ui` dependencies; tokenization reuses the existing synchronous `syntax/shiki.ts`; comment state reuses C4's `review` slice; the pill and query grammar are C3/C1's.

- **`review/diff-source.ts` — the patchset-projection seam, one resolution point.** A typed helper that reads the active patchset's changed files from the resolved review (`Review.patchsets`, selected by `activePatchsetId`) — the projection that arrived through `useCommand("review.load", …)` upstream in `routes/slug.ts`'s `useSlugResolution`. Every diff-file consumer reads through this ONE module; when B3/B4 introduce a dedicated patchset-projection command distinct from the full-review read, `diff-source.ts` is the only file that changes (mirroring how C4 isolated the span-read behind `citations.ts`). Exports the `PatchFile` re-export so callers don't reach into `@rennet/protocol`'s `delta/citations` directly.
- **`review/diff-parse.ts` — unified-diff → hunks, pure.** Parses one `PatchFile.patch` into the `{ oldStart, newStart, lines: { type: "context"|"add"|"del"; text }[] }` hunk shape the renderer consumes, using the repo's established `@@ -a,b +c,d @@` grammar (the same `HUNK_HEADER_RE` `canvas/registrar.ts` already uses — extracted or mirrored, not duplicated ad hoc). `hunkHeader(hunk)` and per-file add/delete counts derive from the projection (`PatchFile.additions`/`deletions` when present, else counted from the parsed hunks). No React, no I/O. The spike's `lib/diff-data.ts` (its `DiffFile`/`DiffHunk` types + fixture) does NOT travel; its `hunkHeader`/`fileStats` *logic* is reborn here over `PatchFile`.
- **`review/diff-view.tsx` — the surface.** Ported from the spike's `diff-view.tsx`: the two-scroll-frame layout (diff cards left, file tree + filter right), the header row (`n files changed`, `+adds −dels`, `StatSquares`, `n / m viewed`), `DiffFileCard` (collapse chevron, mono path with rename `old → new`, status badge, copy-path with 1.5s confirmation and silent clipboard no-op, per-file stats, the **Viewed** checkbox that collapses the card), `FileTree` (folder headers, indented files, per-file stats, strike-through when viewed, jump-on-click), `DiffHunkView` (hunk header, dual `old`/`new` gutters, `+`/`−`/context marker column, tokenized code). `StatSquares` and the empty-filter message port verbatim.
  - **Tokenization through `syntax/shiki.ts`** (`detectLanguage`/`tokenizeDiffLine`), synchronous — NOT the spike's async `lib/code-highlighter.ts`/`getHighlightedLines`. Same reconciliation C4 made for `code-block.tsx`: no `useEffect` fetch, no `ThemedToken[][]` loading state, no pulsing skeleton; the tokenizer already proves itself at production scale in `components/code-view.tsx`.
  - **Line comments via C4.** `DiffHunkView`'s per-line button opens `review/line-comment-editor.tsx` (imported from C4's barrel, spanning the card's full width regardless of horizontal scroll). `onSave` → `setCodeComment`/`clearCodeComment`; `onRequestChanges` → `setCodeComment` + `stageAsk({ anchor: `${path}:${line}`, type: "request-change", body })` — byte-for-byte the contract `review/code-block.tsx` uses. A commented line shows the persistent glyph; a line carrying a matching `review.stagedAsks` entry reads danger red, a plain comment reads evidence green. Read through `selectCodeComments(path)` and `s.review.stagedAsks` — no `useCodeComments()`, no `store?.` guard.
  - **`ProseSelectionLayer` (C4)** wraps the diff scroll frame exactly as the spike wraps it, so Comment/Explain on selected diff text uses the already-landed selection layer. (Ask-staging *logic* over B11 stays C8; C6 only mounts the existing C4 component.)
  - **Deep-link via the query grammar.** The `?file=` param is read through `useSearch` + `readSessionQuery` (fence rule 3 — no `next/navigation`); on mount, the matching card is scrolled into view. The card `id` is `diff-<path>` so the jump is a plain `getElementById().scrollIntoView`.
- **`review/diff-view-container.tsx` (or a `DiffView` wrapper) — the mount.** Reads the active patchset's files through `diff-source.ts` from the review the workspace already resolved, and renders `<DiffView files={…} />`. The review-workspace route gains a minimal `?view` switch: `diff` renders this container; every other value keeps the existing honest placeholder (the board is C5's default branch — see reconciliation 6). This is the only edit outside `review/`.
- **`review/index.ts`** additionally barrels `DiffView` (+ its props type) for the app to import; `app-ui/src/index.ts` already re-exports the barrel.

## Reconciliations against main (packet drift, recorded per the dispatch rule)

1. **The spike's `lib/diff-data.ts` shape is not the projection shape.** The spike renders a pre-parsed `DiffFile`/`DiffHunk`; the real projection is `Patchset.files[]` (`PatchFile`) whose `patch` is a raw unified-diff string. C6 parses `PatchFile.patch` into hunks (`diff-parse.ts`, the repo's own `@@` grammar) instead of importing the fixture, and derives stats from `PatchFile.additions`/`deletions`. The fixture file is read-only reference only.
2. **"Patchset projection via `useCommand`" resolves to the already-landed `review.load`, not a new command.** `review.load` is a landed PURE READ returning the full `Review` (`patchsets[].files[]`, `activePatchsetId`); `routes/slug.ts`'s `useSlugResolution` already runs it and hands the workspace the resolved `Review`. **The packet lists the live patchset as unlanded (B3/B4) — but the raw-diff projection is in fact reachable today** through this read, because the diff carries its full `patch` text inline and needs no span fetch. C6 is still built MemoryBridge-first (every DOM test stubs `review.load`); the genuinely-deferred work is isolated in the Gated cluster (§7). `patchset.readSpan` (C4's `citations.ts` seam, dispatch unbound until B4/B10) is for *citation* hydration and is **not** on the raw-diff path — the diff view never calls it.
3. **`next/navigation` → wouter + `routes/url.ts` (fence rule 3).** The spike's `useSearchParams().get("file")` becomes `readSessionQuery(new URLSearchParams(useSearch())).file`. No `next/*` import enters `app-ui` (the fence stays clean; grep-provable, §7).
4. **`useCodeComments()` and its `store?.` guards do not travel (autopsy S3, fence rule 4).** The diff's line comments read/write the `review` slice directly, through C4's `LineCommentEditor` — the SAME path `review/code-block.tsx` proves. This is precisely what makes the diff-line and board-excerpt comment one object (`review.codeComments[path][line]`), the packet's headline claim.
5. **Tokenization through `syntax/shiki.ts`, not the spike's async highlighter** (same as C4 reconciliation 3): synchronous, no skeleton state, one tokenization pipeline for the whole app.
6. **The mount is a minimal `?view` switch, not a workspace rebuild.** The review workspace is a B2 stub today; C5 owns rebuilding it and its board/default branch. C6 adds only the `diff` branch and leaves the default as the existing placeholder — it never invents board shape. When C5 lands its workspace, the `diff` branch composes with it (the orchestrator serializes the landing); the switch is written so C5 slots the board branch in beside C6's diff branch.
7. **The `Map · Diff` pill is C3's, already shipped.** C6 does not rebuild the pill or the query grammar; it makes the `diff` value render a real surface. "Map·Diff pill in the top bar" (Objective) is satisfied by C3's `top-bar.tsx` + this mount. (The `Map` view is C-later; C6 touches only `diff`.)
8. **Viewed-tracking is local surface state, not a persisted command.** The spike keeps `viewed` in `React.useState`; INVENTORY §4 does not tag a persistence claim, and no `review.*` command records per-file viewed state. C6 keeps it local (Rule Zero — no gate, no ceremony); if a later change wants it durable it adds the command then.
