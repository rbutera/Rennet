## Context

`decideBoundWorkspace` (`packages/server/src/bound-workspace.ts`) is the one place a session's workspace is chosen, and it is called once per session. It has three arms: a pull-request snapshot (`ensurePrSnapshotWorkspace`, detached at the reviewed head, re-pinned in place by `repinBoundWorkspace`), a branch some worktree already has out (`worktreeForBranch`, bound to as-is), and a branch nothing has out (`ensureBranchWorktree` at `branchWorktreePath(dataDir, repoKey, branch)`). The round path captures the successor patchset from the bound root with `headRef: operation.sourceTarget.branch` (`create-server.ts` ~3931), and `submitForgePullRequest` pushes `refs/heads/<headRef>:refs/heads/<headRef>` from `input.repoRoot`.

The settings ladder already declares `worktreeBaseDir` (`DETECTABLE`, no detector since the scout's hint was retired) and `worktreePattern` (`CONFIG_ONLY`), maps them onto the wire as `worktreeRoot` / `worktreePattern`, and writes them through `settings.setProjectValue`. Nothing reads the resolved values.

## Decisions

### D1 — Location resolves off the ladder, and a user-set root is absolute

`worktreeRoot` keeps its registry entry and wire key. Builtin is `join(dataDir, "worktrees")`, computed at resolution time so the preview and the binding agree with whatever `--data-dir` / `RENNET_USER_DATA` produced. The global rung is `daemon-settings.json` → `worktrees.root`, because a filesystem path is a fact about the daemon's host, the same argument that put `tracker` there rather than in client settings. The repo rung is `.rennet/config.json` → `worktreeBaseDir`, the field that already exists. A written value is expanded (`~`) and made absolute by the daemon; a relative value resolves against the data directory. The declaration stays `DETECTABLE`; no detector is added. A changed location applies to sessions created after the change, because a session binds once, and the card says so in one line beside the editor.

*Rejected:* a client-settings rung. A viewer on another machine has no opinion about where a daemon's host keeps checkouts.

### D2 — Layout is two patterns with real tokens, refused when they escape the root

Two keys, both relative to the root. `worktreePattern` (existing) places a branch worktree; tokens `{repo}` (the escaped realpath key, today's middle segment), `{name}` (the resolved remote's repository name, and the repository directory's basename only when no remote resolves — this design first said basename outright, which was wrong: the pull-request placement has always used the forge name, so a clone of `acme/widget` into `/work/widget-local` would have previewed `acme/widget-local/pr-1` while the binding created `acme/widget/pr-1`), `{owner}` (the forge owner when a remote resolves, else `local`), `{branch}` (the branch, its `/` kept as separators). Default `{repo}/{branch}`. `prWorktreePattern` (new) places a pull-request snapshot; tokens `{owner}`, `{name}`, `{repo}`, `{number}`. Default `{owner}/{name}/pr-{number}`. Both defaults are the shapes hardcoded today, so an untouched install places nothing differently, and no migration touches an existing worktree.

A write is refused, with the file untouched, when the pattern carries an unknown token, resolves to an absolute path, resolves to the root itself, or resolves outside the root for any token values (a `..` segment). `branchWorktreePath` and `prWorktreePath` take `(root, pattern, repo, branch|number)`; the old signatures go. The token records are built by `branchTokens` / `prTokens` in adapters, which every bind site AND the preview call, so the set a pattern write blesses cannot drift from the set a binding supplies — a `{owner}` blessed at the write and missing at the bind is a stored pattern that previews fine and throws.

*Rejected:* one pattern for both. A snapshot has a number and no branch; a branch has no number. Forcing one grammar over both produced the empty-token questions this design does not want.

### D3 — The preview is resolved on the daemon and shipped on the row

`settingsProjectSchema` gains additive-optional `worktreePreview: { branch: string; pullRequest: string }`, computed per row from the resolved root, the resolved patterns, the row's real repo key, its real owner/name when a remote resolves, the repository's current branch as the sample (else `main`), and `1` as the sample number. app-ui renders the two strings under the editors and derives nothing. This is the whole answer to why #812's preview lied.

### D4 — `workspace` is a two-valued setting; `own` binds beside the reviewer's checkout on a sibling branch

Key `workspace`, values `share` | `own`, builtin `share`, global and repo rungs (`daemon-settings.json` → `worktrees.workspace`; `.rennet/config.json` → `workspace`).

Under `share` the three arms are unchanged. Under `own`:

- A branch nothing has out: unchanged. Rennet's worktree is on the branch itself; there is no conflict to avoid.
- A pull request: unchanged.
- A branch some worktree already has out: git refuses a second checkout of one branch, so Rennet creates its own worktree on a sibling branch `rennet/<branch>` forked from the branch's current head.

**The first draft of this decision got the sibling's PLACEMENT and its LIFECYCLE wrong, and both were destructive.** What it said, and what is true instead:

- **The sibling has its OWN path.** The first draft placed it at `branchWorktreePath(root, pattern, repo, branch)` — the path a Rennet BRANCH worktree of the same repository already occupies. It is `branchWorktreePath(root, pattern, repo, "rennet/<branch>")`: the branch pattern applied to the sibling's own name. One path per ref.
- **`own` asks WHOSE checkout already has the branch out.** When that worktree is Rennet's own branch worktree — under the resolved root, at the branch's computed path, and not the repository root — it is not the reviewer's tree, so the bind takes it exactly as `share` would. Only a checkout Rennet did not place runs the sibling arm. Without this, a second session under `own` forked a workspace away from the one the first session was committing in, and switched that worktree onto the sibling underneath it.
- **Sessions share a sibling exactly as they share a checkout.** One sibling worktree per (repository, branch). A second `own` session binds to the existing sibling AS IT IS: no `reset --hard`, no `checkout`, nothing that touches its working tree or index. The first draft re-forked on every bind, so a second session discarded whatever the first had in flight.
- **Re-forking happens only when the sibling BRANCH exists with NO worktree.** If it is reachable — from the branch, or from any remote-tracking ref of the branch — the stale branch is deleted and recreated at the branch's head, so a fresh session starts from the branch's current tip. If it is ahead, `worktree add` at the existing sibling branch and keep it: those commits are on no other ref.
- **Rennet never operates inside a directory that is an existing worktree on something else.** If the computed sibling path is already a registered worktree of the repository on any other ref — the reviewer's, a Rennet branch worktree, a detached pull-request snapshot — the bind THROWS naming the path and the ref, and nothing is created or checked out. This also covers a pattern with no `{branch}` token, which computes one path for every branch and can resolve onto the reviewer's own repository. **The pull-request snapshot answers the same way**: `ensurePrWorktree` replaces a superseded checkout only when it is DETACHED and Rennet's own pull-request index records a snapshot at that path, and throws otherwise. Both patterns are the reviewer's to set and both resolve under one root, so they can be made to collide — and the replacement was a `worktree remove --force` plus an `rm -rf`, which is a reviewer's uncommitted work deleted by the ordinary act of opening a pull request.
- **NO BIND PRUNES A WORKTREE REGISTRATION — neither of them.** `git worktree prune` drops a registration whose directory git cannot reach *right now* — an unmounted volume, a network share that is down, a distro that is not running — and none of those means the worktree is gone. The sibling bind pruned, then re-forked or recreated, and the staged-only work in the old directory belonged to no registration when the volume returned. **The BRANCH bind had the same defect one arm over, and it survived the first fix:** it tested `existsSync(<worktree>/.git)`, which is false for exactly that unreachable-but-present directory, then pruned and ran `worktree add` *over the mount point*. Both binds now READ `git worktree list --porcelain -z` instead, and answer three ways: registered and reachable is the workspace (checked out onto the branch if it has drifted); registered and unreachable is a throw naming the path and git's own reason, with nothing created, checked out or pruned; not registered is a plain `worktree add`. "Unreachable" is git's `prunable` annotation where git prints one — **and where it does not, a probe, because the annotation needs git ≥ 2.36 and an older git's silence would otherwise record a directory that is gone as a session's workspace for its whole life.** The probe is `git rev-parse --show-toplevel` run *at the record's own path*, which asks inside the repository's locus, unlike an `existsSync` on this side. Pruning happens in ONE place, the daemon-start sweep (D5).
- **The daemon's spelling is what gets recorded.** `git worktree list` prints paths in the spelling of the git that answered, which on a Windows daemon driving a WSL repository is not the spelling the daemon addresses the repository by. Every arm that binds to a worktree git named re-spells it — the computed placement when it is the same directory, `inRepoSpelling` otherwise — so `boundRoot` is always a path this daemon can `existsSync`, detect a locus for, and compare against its own worktree root.

The session records `workBranch` beside `boundRoot`: the branch itself under `share` or under `own`'s first two arms, the sibling under the third. Every consumer that today assumes "the session's branch" is a ref in the bound root reads `workBranch` instead:

- **The round.** The turn commits in the bound root, which has the sibling checked out, so commits land on the sibling without the worker knowing. The successor patchset is captured from the bound root with `headRef: <branch>` — the reviewed branch's NAME, which is what the review and the pull request are about — and `headOid` from the sibling's tip, exactly as today's `operation.state.commits.to`. **The round's workspace planner matches its candidate root by `workBranch`, not by the round's source target.** The first draft matched by `sourceTarget.branch`, so the sibling failed the match and the search fell through to the reviewer's checkout, where the worker committed on the reviewed branch and the patchset was captured from it. A session that HAS a bound root does not search at all: the binding is the workspace, and a bound root that is not on the work branch is a thrown error naming both, never a fallback to another candidate.
- **The pull-request push.** `submitForgePullRequest` takes `workBranch` and pushes `refs/heads/<workBranch>:refs/heads/<headRef>`. Under `share` the two names are equal and the refspec is byte-identical to today's. Before pushing, Rennet asserts the work branch is the reviewed branch itself or exactly its sibling; anything else is a session whose binding and review have come apart, and the throw names both. The push records `{ remote, branch }` on the session — a DESTINATION, not a timestamp, because every question later asked of it is a question about what a ref holds now.
- **What the surface says.** `session.workBranchState` is a READ, computed from git at request time: `aheadOfBranch` (commits the sibling holds that the branch does not, `refs/heads/<branch>..refs/heads/<workBranch>`), `behindRemote` (commits the recorded push destination's ref holds that the branch does not, `refs/heads/<branch>..refs/remotes/<remote>/<branch>`), `pushed` (the sibling's tip is reachable from `refs/remotes/<remote>/<branch>` for the recorded remote), `landed` (the branch already CONTAINS the sibling's tip — ancestry, not equal tips, so it stays true after the reviewer commits or pulls on top of a landing), and the remote-tracking ref it decided against, named. The two counts are separate because the two sentences are about two ranges: a first draft spent one number on both and rendered the sibling's count under "`feat/x` is behind `origin/feat/x` by N", which is right only until somebody else pushes. And it is re-read on the events that move those refs — a settled round and a pull-request submission both invalidate it — because a cached answer is exactly the durable claim this read replaced. It replaced a durable `workBranchPushedAt` stamp, which went on claiming the branch was behind after a landing or a pull had made that false. The note is mounted **wherever the review workspace shows the session's branch**, not only in the round greeting: the gap is open from the round that made it until the reviewer lands or pulls.
- **Landing locally.** `session.landWorkBranch` runs `git merge --ff-only <workBranch>` INSIDE the worktree that has the branch out (the reviewer's checkout). Git decides what happens, and Rennet invents no refusal of its own. A diverged branch — the reviewer committed on it meanwhile — is refused by git and reported verbatim, with the action still offered. **Uncommitted changes are NOT a refusal Rennet adds:** `merge --ff-only` accepts unrelated uncommitted work and carries it across, and refuses only when the merge would overwrite a file the reviewer has edits in. The first draft of this design said the action ran "only when git agrees the tree is clean", which is not what git does and would have been a gate if implemented. Rennet does not merge or rebase on the reviewer's behalf.

*Rejected:* a detached workspace committing on a detached HEAD. Its commits are reachable only through a worktree's HEAD and the reflog, and `worktree prune` or `gc` can lose them; a branch is a ref the reviewer can see in `git branch` and recover from. *Rejected:* an `auto` value that picks `own` when the reviewer's checkout is dirty at bind time. It felt clever, which Rule Zero names as the signal to stop, and it makes the workspace a function of state the reviewer did not choose. *Rejected:* refusing to bind while the reviewer's checkout holds the branch. A gate. *Rejected:* a cleanliness check before the land action. Also a gate: git already answers, and a Rennet-invented refusal where git would comply is exactly what Rule Zero forbids.

### D5 — Sibling cleanup is reachability, never deletion of unmerged work, and never of a claimed workspace

On `session.archive`, when the session's `workBranch` is a sibling: if the sibling's tip is an ancestor of the local branch OR of a remote-tracking ref of that branch (the push under `own` makes the latter true), the worktree is removed and the sibling deleted. Otherwise both stay and the inventory row reads "ahead of `<branch>` by N commits". Nothing forces. The startup sweep applies the same rule to siblings whose sessions are gone.

Three things the first draft did not say, each a review finding:

- **Collection needs no live claimant.** A sibling is shared by every session on that (repository, branch), so archiving one of them must not remove the directory another is committing in. The sweep always asked; the archive did not. Both do now, and a kept sibling says so in the daemon log.
- **Reachability is read from GIT, from the ACTUAL push destination.** `<branch>@{upstream}` was wrong: Rennet's push sets no upstream (no `-u`, deliberately — writing branch config into the reviewer's repository is not this action's business), so the configured upstream was absent on exactly the repositories the question is asked about and the rule answered false forever. What the push does update is `refs/remotes/<remote>/<branch>`, which the session records at the push. Collection checks `refs/heads/<branch>`, then that recorded remote's ref; the sweep, which has no session to ask, checks every `refs/remotes/*/<branch>`.
- **A collected sibling clears the session's recorded workspace.** A recorded root that is no longer on disk is not a binding, it is a pointer at a deleted directory. Cleared, a later un-archive re-runs `decideBoundWorkspace` and records a fresh binding. This is the ONE case a session re-binds, and un-archiving also clears a recorded root that has gone missing some other way (a sweep, which had no session record to clear).

**Rennet prunes only registrations it placed, and only from the daemon-start sweep.** This is the whole of the prune rule, and there is exactly one site that runs `git worktree prune` (the sibling bind's was removed, the branch bind's was removed, and the legacy-zoo sweep's was removed). The sweep prunes a registration only when all three hold:

- **git reports it unreachable** — `prunable` in `worktree list --porcelain`. A git too old to print the annotation says nothing, and here silence reads as *present*: the mistake this guard exists to prevent is a prune, so the cheap direction is to leave an admin entry lingering. (The binds resolve the same silence the other way, with a probe, because *their* mistake is binding a session to a directory that is gone.)
- **it is Rennet's own** — its path is under the repository's resolved placement root, OR its branch is `rennet/*` (a pattern change can move the root out from under a sibling Rennet still owns). **A registration that is not Rennet's is never pruned by Rennet, reachable or not.** The reviewer's worktree on an unmounted volume is theirs; `git worktree repair` is their tool for it.
- **no live session claims it.** A claim is matched two ways, either sufficient: by **work branch** — `session.workBranch === record.branch` in the same repository, which needs no path at all and survives a session whose recorded spelling never matched git's — and by **path in both spellings**, the daemon's and git's, through `inRepoSpelling`. The path comparison resolves the deepest ancestor that still exists and re-attaches the tail, because the directory in question is *missing* and plain `realpath` refuses both sides: on macOS git prints `/private/var/…` where the daemon records the `/var/…` symlink, and a raw string compare pruned a registration a live session was bound to.

**And the guard is all-or-nothing over EVERY unreachable registration in the repository, Rennet's or not.** `git worktree prune` takes no path — it is repo-wide, and there is no scoped verb for a registration whose directory is missing (`worktree remove` wants the directory to be there). So one unreachable registration that fails either test means the repository gets no prune at all this pass, and the log names the paths that held it, capped at five with the total. Guarding only on the claim, and only against Rennet sessions' paths, is how one reviewer's unmounted worktree was dropped as collateral for pruning one of ours.

Both paths write one sentence per decision to the daemon log — `SiblingCollection.reason`, which is documented for exactly that — and the sweep writes its counts. "Collected nothing" and "failed on every repository" were otherwise the same silence, which is the shape the sweep's own temporal-dead-zone bug wore for a release.

### D6 — The inventory is read from git and the session store, and computed on request

`worktrees.list({ repoPath })` returns one row per workspace Rennet knows for that repository: `git worktree list --porcelain` filtered to paths under the resolved root plus the PR index plus any `boundRoot` recorded on a session of that repository (which is how the reviewer's own checkout appears, tagged `own checkout`, with no remove action). Each row: `id` (an opaque digest of the workspace's resolved path, computed on the host — the row's ADDRESS, so a projected client that only ever sees a repo reference can still name a row), `path` (display), `kind` (`own-checkout` | `branch` | `sibling` | `pull-request`, decided from the QUERIED repository root and the row's own ref/index facts, never by exclusion and never from git's first record — a project rooted at a linked worktree would otherwise show two rows both reading "your own checkout"), `ref`, `sessionIds` (capped at 20 with `sessionsTruncated`), `createdAt` (a linked worktree's `.git` FILE mtime, the main checkout's `.git` birth time, and absent when neither is knowable — a `.git` directory's mtime advances on every commit and is not a creation date), `lastUsedAt` (the latest bound session's activity), `sizeBytes` (a bounded `du`, capped at 2 s per row, `undefined` past the cap and the cell says "—"), and on a sibling D5 will not collect, `keepsBranch` — one capped sentence saying the removal keeps `rennet/<branch>`, and why, since `aheadOf` has no count to carry when the reviewed branch has been deleted. `worktrees.remove({ repoPath, id })` runs `git worktree remove` without `--force` and returns git's refusal verbatim when there is one — verbatim to a local client, and with any absolute path outside the known roots and the home dir redacted to a projected one (R19, the same treatment `session.transcript` gets). D5's rule gates the sibling BRANCH, not the worktree: an unmerged sibling loses its worktree and keeps its branch, and the outcome says so. Only the automatic collection (archive, sweep) keeps both. Both are direct reads and writes with no confirmation (settings-resolution: no ceremony on any control). The list reflects a project→repo mapping, so every call names `repoPath`, never a project id (CLAUDE.md: a workspace maps many repos to one identity).

## Risks / Trade-offs

- **A pattern edit on a repository with live sessions.** Existing sessions keep their recorded `boundRoot`; new ones use the new layout; both show in the inventory. No relocation is attempted. Documented on the card in one line.
- **`{owner}` with no forge remote.** Resolves to `local`, stated in the token help. A repository with two forge remotes uses the same resolution `resolveForgeRemote` already makes for submission.
- **The land action's fast-forward runs in the reviewer's checkout.** This is the one place `own` mode writes to the reviewer's tree, and it does so only on the reviewer's click and only as a fast-forward. What stops it is git: a diverged branch is refused, and so is a merge that would overwrite a file the reviewer has uncommitted edits in. Unrelated uncommitted work rides along, as `merge --ff-only` allows — Rennet adds no refusal of its own. This is the trade-off `own` exists to make explicit.
- **Two repositories in one workspace, both on `feat/x`, one in `own`.** The binding is per repository (the review carries `repositoryRoot`), so the settings resolve per repo rung and the siblings are per repository. The fixture in task 2.8 is the proof, and it is the fixture the 2026-08-28 rule demands.
