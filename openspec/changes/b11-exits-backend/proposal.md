## What this change does

Builds the **engine side of the three exits** (R29–R36). The marquee is **durable host-side asks**: the reviewer's staged asks, line comments, quote threads, retired ledger and verdict override are **client-only and transient today** (`app-ui/src/store/review.ts` — "no persist: reload resets interaction clean"), so a reload loses the whole review. B11 moves them host-side behind **one write path — tool call → event log → projection** — so they survive reload, with **receipt-is-undo** on every mutation (Q15, decided).

The egress is **already live and is not rebuilt**: `dispatch/publish.ts` implements `publish.compose` (review + pr), `publish.review`, `publish.submitPr` with consent-token binding, exact-preview (R33), single-flight and compositionId staleness; `core/` already carries `draft-pr-body`, `publish-review` (two-strata composition), `publish-submission`, and `handoff-compose`/`handoff-loop` (the round work-order). B11's job over that base:

- **Durable asks**: an append-only per-session ask event log + a fold to the current ask projection, a file-backed store (B10 precedent), and the `ask.*` command surface that is the sole writer. Receipt-is-undo. Emitted to clients (private + R19 projected).
- **Compose from the durable projection**: extend `publish.compose` so the two-strata review and the PR-body draft source the living draft from the durable ask projection — the swap `app-ui/src/handoff/handoff-data.ts` was built to absorb (its own line: "THIS is the only file that changes").
- **Round work-order dispatch**: the round-dispatch command composes the dispatched asks into **one** work-order via `handoff-compose`, **serialized per session** (one round in flight), idempotent (dispatch twice → one dispatch). This **wires `createRoundsRuntime` + `SessionEntry` into `create-server`** — the trigger B9 explicitly deferred (tasks 5.1/6.2, "lands with the round trigger").
- **Living-draft rework + PR ripening**: the real span-rework command backing the client's gated `reviseDraftSpan` seam, dispatched as a one-shot worker through **B9's `ReworkQueue`** with **quote-match carry** (re-anchor via `core/lineage-matcher`); the own-branch PR draft **ripens across rounds** (re-compose + re-raise publish-ready as each round lands).
- **Nothing posts without Rai clicking post**: preserved unchanged — draft/preview/post language; pushing a branch is not publishing.

## Review-fix ledger (dual-review PR #537 — opus REQUEST-CHANGES / Codex BLOCK, all upheld under Rule Zero)

Each entry is a fix, not a gate: data-loss prevention, honest failure, correctness, privacy, or test-validity.

1. **P0 — corrupt durable history silently became an empty review** (`adapters/ask-log-store.ts`). `read` caught EVERY failure as "absent", so a torn write / malformed JSON / schema or version mismatch / foreign-session or non-contiguous seq folded to an empty projection → compose posted a CLEAN review over lost asks (silent lie). Fixed: ONLY ENOENT is absent; every other state is `corrupt` and `read`/`readProjection` throw `AskLogCorruptError` while `append` refuses to clobber. Added `readState` validation (version + per-event session identity + contiguous seq) and a parent-directory fsync after rename (crash-durable rename, a genuine ~4-line addition — no transaction machinery, per the B09 precedent). Proof: `ask-log-store.test.ts` — torn-write refusal, version/foreign-session/seq refusal, and a **child-process** SIGKILL'd-mid-write durability test (finding 10a).

6. **P1 — receipt-is-undo failed for duplicate identities** (`core/exits/ask-projection.ts`). `stage` and `quote-open` OVERWRITE an existing id in the fold, but their receipts always deleted (`unstage` / `quote-close`) — so applying a receipt after re-staging an existing id removed the ORIGINAL ask/thread instead of restoring it, breaking the receipt-is-undo invariant the doc-comment claims for ANY event. Fixed: both receipts now carry the prior ask/thread when one existed (restore it), matching the `line-comment-set` "restore the prior value" inverse. Proof: `ask-projection.test.ts` — duplicate-identity overwrite round-trips added to the receipt-is-undo table.

5. **P1 — replicated serializer was not a complete write boundary (LOST UPDATE)** (`server/dispatch/rework.ts`). The per-review tail serialized `review.reviseSpan` against itself, but an ordinary `ask.edit` landing WHILE the one-shot worker was awaited was silently overwritten by the stale rework result on completion (Codex reproduced this). Also the worker's output replaced the ENTIRE ask body, so revising one sentence deleted the surrounding prose. Fixed: (a) a compare-and-swap on the ask body — re-read after the worker and DISCARD the rework (honest `unavailable`, "changed while the rework was running") if the body changed, so the newer edit stands; (b) SPLICE the refined span back into the full body in place rather than replacing it wholesale. The 5.1 ask-log architecture stays; the write boundary is now real. Proof: `rework-dispatch.test.ts` — a reproduced race (manual `ask.edit` during the worker is preserved, rework discarded) + a splice test proving surrounding prose survives.

3. **P1 — round.dispatch idempotency keyed on a nondeterministic digest** (`server/dispatch/round.ts`). The live composer ran BEFORE the memo lookup and the key was the COMPOSED work-order digest = a hash over model-authored titles/order → nondeterministic, so a double-click / reconnect / retry re-composed to a different key and kicked the coding runtime TWICE (Codex reproduced this). The key also omitted the patchset. Fixed: coalesce BEFORE the live composer on the DETERMINISTIC input digest (`bundle.digest`, a content hash over the sorted addressed dispositions) PLUS `bundle.patchsetId`; the memo now holds the composed order so a repeat returns it without recomposing. Proof: `b11-exits-e2e.test.ts` — a NONDETERMINISTIC live composer injected, two identical dispatches coalesce to ONE compose + ONE kick. **FLAGGED (3c):** durable cross-restart dispatch-identity persistence is NOT included — the in-process memo makes the reproduced same-process race idempotent, but a restart re-drives a completed dispatch. There is no durable dispatch-identity store wired (rounds.ts `dispatchRound` only serializes); adding one is a new persistence seam through `create-server`, out of a surgical scope. Ledgered as a scoped follow-up (evidence: `runtime/rounds.ts` `dispatchRound` has no `loadDraftedBoards`-style durable read).

4. **P1 — failed rounds became memoized successes; success ripened stale state** (`server/create-server.ts` dispatchRound wiring). The `runWorkers` closure ignored `runHandoffTurn`'s status, so a `{status:"failed"}` turn resolved the round → `round.dispatch`'s key stayed memoized → an identical retry was suppressed; and the ripening decision/compose used the pre-round review closure. Fixed: THROW on `outcome.status === "failed"` so the kick rejects and the memo evicts (retryable — the rounds tail still swallows the rejection so the session queue is not wedged); reload the review by id before ripening so the re-compose runs over current state. Proof: `round-dispatch.test.ts` — a failed worker rejects the round without wedging the session + a successful round ripens; the round.ts kick-eviction test proves the memo drops a failed key.

8. **P1 — exit lanes not disjoint (team PRs / retrospectives could dispatch coding rounds)** (`server/dispatch/round.ts`). No own-branch check, so a teammate-PR ask could enter BOTH the GitHub-review exit AND the round work-order exit. Fixed as HONEST ROUTING (not a gate): `round.dispatch` returns an empty order (`dispatched:false`) unless the review is own-branch — reusing the SAME `postTarget.viewerDidAuthor` signal the Hand off toggle routes on (own-PR ownership fact landed on main `eea4e398`; folded in before the final gate). Own-branch = not retrospective AND (no postTarget OR viewerDidAuthor true); fail-safe to teammate when absent. Proof: `round-dispatch.test.ts` — a teammate PR (viewerDidAuthor false) refuses, an own PR (viewerDidAuthor true) dispatches.

2. **P0 — review composition silently dropped the body stratum** (`core/publish-review.ts`). `reviewCommentsFromProjection` discarded every ask whose anchor was not `path:line` — a prose/quote-anchored request-change entered the round work-order but VANISHED from the team-review preview + posting (lost reviewer intent, violating handoff-and-exits.md "The review's two strata"). Fixed: added `reviewBodyNotesFromProjection` — the exact complement of the line-comment path, so the two PARTITION `stagedAsks` (each ask appears EXACTLY ONCE, line comment OR body note). Body notes are woven into the review body under a "Review notes" heading, each ledgered (`body-note`, never a silent drop), fold into the canonical payload (a new `bodyNotes` field OMITTED when empty, so the ui byte-pin is unchanged until the client sends them), and escalate the verdict (a prose request-change makes REQUEST_CHANGES). Threaded through `publish.compose` → `publish.review` → `assertCompositionFresh`. Proof: `publish-compose-asks.test.ts` (partition: each ask once), `publish-review.test.ts` (body weave + ledger + verdict escalation), `b11-exits-e2e.test.ts` (a prose ask appears EXACTLY ONCE in the outbound request body — finding 10c).

7. **P1 — durable model could not preserve a deletion-side (LEFT) comment; VERDICT: regression.** INVESTIGATED (git-blame): the pre-B11 `reviewCommentsFromDispositions` mapped `anchor.side` (`deletions` → LEFT) + spans; B11's `publish.compose` swap to the durable staged-ask projection (commit 9d3550b9) hardcoded RIGHT single-line, so a deletion-side ask posts to the wrong side. This is a real regression in the compose SOURCE. Fixed additively (no breaking client change): `StagedAsk` gains an optional `side: "LEFT"|"RIGHT"`; `reviewCommentsFromProjection` honors it (`ask.side ?? "RIGHT"`) and `handoffDispositionsFromProjection` maps `LEFT → deletions`. Proof: `publish-compose-asks.test.ts` — a deletion-side ask composes to LEFT, a default ask to RIGHT. **LEDGERED follow-up (evidence):** the CLIENT (C9/app-ui, out of this gate) must populate `side` when staging a deletion-side finding; and a multi-line RANGE (`startLine < line`) round-trip needs `ReviewCommentInput` to model a start line (it carries a single line today) — a bounded follow-up, not silently shipped as faithful (the limitation is documented in the schema + compose).

9. **P2 — R19 path scrub missed the pushed projection (host-path leak)** (`server/dispatch/ask.ts`). Anchors + line-comment record KEYS accepted arbitrary strings; the projection scrub keeps object keys + only substitutes known roots, so an unknown absolute path (`/etc/passwd`) survived into the pushed R19 projection. Fixed at INGESTION (the strongest fix — the data never enters): `ask.stage` validates a code anchor's path (a whitespace-free `path:line`) and `ask.setLineComment` validates its path key as repo-relative (`isRepoRelativePath`), rejecting absolute/traversing paths before they reach the log — matching the `canvas.disposition` ingestion + `publish.compose` egress precedent. Prose anchors (free text) are untouched (the general model-prose honesty, not a structural path). Proof: `ask-dispatch.test.ts` — an absolute code anchor + a traversing line-comment key are refused (nothing written), while repo-relative + prose anchors are accepted (no false rejection).
